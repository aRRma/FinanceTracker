# Личный трекер финансов — требования и план реализации

Версия документа: 1.0
Статус: принято к реализации

---

## 1. Назначение и границы

### 1.1 Назначение

Мобильное приложение для персонального учёта личных финансов: счета, категории расходов и доходов, операции, текущие балансы. Пользователь — один человек, использующий несколько собственных устройств.

### 1.2 Ключевое свойство

Приложение работает полностью автономно. Источник правды — локальная база на устройстве. Сервер выполняет только роль хранилища для обмена данными между устройствами пользователя и не содержит бизнес-логики.

### 1.3 Границы MVP

**Входит:** счета, двухуровневые категории, операции трёх видов, балансы, ручная синхронизация между устройствами.

**Не входит:** аналитика и отчёты, теги, вложения, операции с датой в будущем, повторяющиеся операции, бюджеты, цели накопления, импорт из сторонних приложений, поиск и фильтры, экспорт, блокировка приложения, iOS.

## 3. Доменная модель

### 3.1 Счёт (Account)

| Поле | Тип C# | Тип БД | Описание |
|---|---|---|---|
| `key` | `Guid` | `uuid` / `TEXT` | UUIDv7, генерируется клиентом, первичный ключ |
| `name` | `string` | `text` | Наименование |
| `type` | `enum` | `text` | Наличные или карта. Влияет только на отображение |
| `currency` | `enum` | `char(3)` | RUB, USD или EUR |
| `opening_balance` | `decimal` | `numeric(19,2)` | Начальный остаток |
| `opened_on` | `DateOnly` | `date` | Дата, с которой действует начальный остаток |
| `excluded_from_totals` | `bool` | `boolean` | «Скрыть из расчётов»: счёт не входит ни в подытог доступных к тратам, ни в итоги дня в ленте |
| `sort_order` | `int` | `integer` | Порядок на главном экране |
| `created_at_utc` | `DateTimeOffset` | `timestamptz` | |
| `updated_at_utc` | `DateTimeOffset` | `timestamptz` | |
| `deleted_at_utc` | `DateTimeOffset?` | `timestamptz` | Надгробие мягкого удаления |
| `synced_at_utc` | `DateTimeOffset?` | `timestamptz` | Подтверждение доставки на сервер |
| `external_id` | `string?` | `text` | Резерв под будущий импорт |

### 3.2 Категория (Category)

| Поле | Тип C# | Тип БД | Описание |
|---|---|---|---|
| `key` | `Guid` | `uuid` / `TEXT` | UUIDv7; для категорий пресета — детерминированный UUIDv5 |
| `parent_key` | `Guid?` | `uuid` | Заполнен только на втором уровне |
| `level` | `int` | `smallint` | 1 или 2 |
| `kind` | `enum` | `text` | Доход или расход. Задаётся только на первом уровне |
| `name` | `string` | `text` | |
| `icon` | `string` | `text` | Устойчивый ключ значка из набора, зашитого в приложение |
| `exclude_from_reports` | `bool` | `boolean` | Для служебных категорий |
| `created_at_utc`, `updated_at_utc`, `deleted_at_utc`, `synced_at_utc`, `external_id` | | | Как у счёта |

Ссылка операции на мягко удалённую подкатегорию допустима. Она возникает, когда одно устройство удалило подкатегорию, а другое офлайн записало в неё операцию. Такая операция отображается с названием удалённой подкатегории, а сама подкатегория в списках выбора не предлагается. Перенос в «Прочее» по INV-20 выполняется только на устройстве, где пользователь подтвердил удаление, и не переигрывается при получении изменений: иначе слой синхронизации исполнял бы доменные правила вопреки SYN-18, и устройства разошлись бы между собой.

### 3.3 Место (Place)

Справочник контрагентов: магазины, работодатели, банки, клиники. Одна операция ссылается не более чем на одно место.

| Поле | Тип C# | Тип БД | Описание |
|---|---|---|---|
| `key` | `Guid` | `uuid` / `TEXT` | UUIDv7 |
| `name` | `string` | `text` | |
| `created_at_utc`, `updated_at_utc`, `deleted_at_utc`, `synced_at_utc`, `external_id` | | | Как у счёта |

Ссылка операции на мягко удалённое место допустима и не считается нарушением целостности. Массовое обнуление ссылок при удалении места запрещено: оно изменило бы сотни строк операций, поставило их в очередь отправки и породило искусственные конфликты построчного слияния.

### 3.4 Операция (Transaction)

| Поле | Тип C# | Тип БД | Описание |
|---|---|---|---|
| `key` | `Guid` | `uuid` / `TEXT` | UUIDv7 |
| `kind` | `enum` | `text` | Доход, расход или перевод |
| `account_key` | `Guid` | `uuid` | Основной счёт |
| `counter_account_key` | `Guid?` | `uuid` | Счёт назначения, только для перевода |
| `amount` | `decimal` | `numeric(19,2)` | Всегда положительная |
| `counter_amount` | `decimal?` | `numeric(19,2)` | Только для перевода |
| `category_key` | `Guid?` | `uuid` | Категория второго уровня |
| `place_key` | `Guid?` | `uuid` | Место. Необязательно, запрещено для перевода |
| `occurred_on` | `DateOnly` | `date` | Календарная дата операции |
| `note` | `string?` | `text` | До 1000 символов |
| `created_at_utc`, `updated_at_utc`, `deleted_at_utc`, `synced_at_utc`, `external_id` | | | Как у счёта |

### 3.5 Конвенции

- Суффикс `_at_utc` — момент времени, всегда UTC.
- Суффикс `_on` — календарная дата, без времени и часового пояса.
- Все внешние ссылки идут на `key`. Иных идентификаторов у сущностей нет.

## 4. Инварианты доменной модели

### 4.1 Операции

| INV-01 | Суммы всегда положительны. Знак определяется видом операции, а не знаком суммы |
|---|---|
| INV-02 | `amount` строго больше нуля |
| INV-03 | `counter_account_key` и `counter_amount` заполнены тогда и только тогда, когда вид операции — перевод |
| INV-04 | В переводе счета источника и назначения не совпадают |
| INV-05 | Если валюты счетов перевода совпадают, `amount` и `counter_amount` равны |
| INV-06 | Категория обязательна для дохода и расхода, запрещена для перевода |
| INV-07 | Категория операции всегда второго уровня |
| INV-08 | `occurred_on` не раньше `opened_on` обоих задействованных счетов |
| INV-09 | `occurred_on` находится в диапазоне от 2000 года до текущей даты включительно |
| INV-10 | Длина заметки не превышает 1000 символов |
| INV-22 | Место необязательно для дохода и расхода и запрещено для перевода |

### 4.2 Счета

| INV-11 | Валюта счёта не может быть изменена после появления первой операции по нему. Мягко удалённые операции учитываются наравне с живыми: достаточно, чтобы операция по счёту существовала когда-либо |
|---|---|
| INV-12 | `opened_on` может быть сдвинута назад свободно; вперёд — только при отсутствии операций раньше новой даты |

INV-11 не закрывает многоустройственную гонку целиком: другое устройство может держать офлайн неотправленную операцию по счёту, невидимую проверке. Учёт удалённых операций сужает окно до случая, когда операция никогда не доезжала.

### 4.3 Категории

| INV-13 | Дерево категорий имеет ровно два уровня |
|---|---|
| INV-14 | Подкатегория обязана ссылаться на группу; группа ни на что не ссылается |
| INV-15 | Вид (доход или расход) задаётся на первом уровне и наследуется вторым |
| INV-16 | Подкатегория может быть перенесена в другую группу того же вида |
| INV-17 | Подкатегория не может быть повышена до группы |
| INV-18 | У каждой группы существует подкатегория «Прочее». Исключение — служебные группы, чья единственная подкатегория неудаляема |

### 4.4 Правила изменения

| INV-19 | Редактирование операции — замена состояния целиком. Изменению подлежат все поля, включая вид операции |
| INV-25 | Смена вида операции немедленно стирает поля, запрещённые новым видом: при переходе в перевод — категорию и место, при переходе из перевода — счёт назначения и вторую сумму. Скрытого состояния не сохраняется: возврат прежнего вида требует ввести поля заново |
|---|---|
| INV-20 | Удаление подкатегории переносит её операции в «Прочее» той же группы |
| INV-23 | Подкатегории «Прочее» и служебные «Разница» не удаляются и не переносятся в другую группу: без «Прочего» группа теряет приёмник для операций удаляемых подкатегорий |
| INV-24 | Сумма операции не превышает 999 999 999 999,99 в валюте счёта |
| INV-21 | Удаление любой сущности выполняется мягко — проставлением `deleted_at_utc` |
| INV-26 | Имена уникальны среди неудалённых записей: счёт — по всему списку, группа — среди групп своего вида, подкатегория — внутри своей группы, место — по всему справочнику. Сравнение без учёта регистра, окружающие пробелы обрезаются. Нарушение блокирует сохранение |

| FR-TRX-03 | Создание перевода: счёт источника, счёт назначения, сумма; вторая сумма запрашивается только при различающихся валютах |
| FR-TRX-04 | Редактирование операции с возможностью изменить вид |
| FR-TRX-05 | Удаление операции с обязательным подтверждением |
| FR-TRX-06 | Подстановка в форму создания последнего использованного счёта и текущей локальной даты |

### 5.3.1 Места

| FR-PAY-01 | Указание места при создании и редактировании операции |
|---|---|
| FR-PAY-02 | Ввод места с подстановкой ранее использованных значений по мере набора |
| FR-PAY-03 | Создание нового места прямо из формы операции, без перехода в справочник |
| FR-PAY-04 | Переименование места. Изменение отражается во всех операциях без их правки |
| FR-PAY-05 | Удаление места. Строки операций не изменяются: операции с удалённым местом отображаются как операции без места, в подсказках оно не предлагается |
| FR-PAY-06 | Порядок в подсказках определяется частотой использования |

### 5.4 Балансы и главный экран

| FR-BAL-01 | Баланс счёта равен начальному остатку плюс доходы, минус расходы, минус исходящие переводы, плюс входящие переводы. Учитываются все неудалённые операции без ограничения по дате: фильтр «не позже текущей даты» отсекал бы только операции, полученные с устройства в часовом поясе восточнее, и разводил балансы на сутки |
|---|---|
| FR-BAL-02 | Главный экран группирует счета по валютам |
| FR-BAL-03 | Внутри каждой валюты отображается один подытог: доступно к тратам. В него входят счета без признака «скрыть из расчётов» |
| FR-BAL-04 | Аннулировано. Подытог накоплений упразднён вместе с FR-BAL-03: счёт, скрытый из расчётов, не должен попадать и в отдельную сумму. Номер сохранён и повторно не используется |
| FR-BAL-05 | Единая сумма по всем валютам не вычисляется и не отображается |
| FR-BAL-06 | Отрицательный баланс допустим и не сопровождается предупреждением |

### 5.5 Лента операций

| FR-LED-01 | Просмотр операций по выбранному счёту |
|---|---|
| FR-LED-02 | Порядок — от новых к старым. Внутри одной даты — по `created_at_utc` убывающе; при равных значениях ничья разбивается ключом. Ключ в сортировке нужен для совпадения порядка на разных устройствах: `created_at_utc` ставится часами записавшего устройства без коррекции (SYN-16) и может совпасть |
| FR-LED-03 | Перевод отображается в ленте обоих задействованных счетов с корректным знаком и суммой в валюте соответствующего счёта |
| FR-LED-04 | Загрузка ленты выполняется постранично |
| FR-LED-05 | Общая лента по всем счетам показывает перевод одной строкой — со стороны счёта-источника. Итог дня считается в рублях по счетам без признака «скрыть из расчётов»; перевод входит в него как расход счёта-источника. Строки по счетам в других валютах в ленте видны, но в итог не входят: единой суммы по валютам не существует (FR-BAL-05, NFR-10) |

### 5.7 Настройки

| FR-SET-01 | Часовой пояс определяется системой устройства с возможностью переопределения вручную |
|---|---|
| FR-SET-02 | Адрес сервера синхронизации и токен доступа задаются в настройках |
| FR-SET-03 | Тема оформления: системная, светлая, тёмная. По умолчанию системная. Настройка локальная, между устройствами не передаётся |

## 6. Требования к синхронизации

### 6.1 Модель данных обмена

| SYN-01 | Источник правды — локальная база устройства |
|---|---|
| SYN-02 | Курсор — монотонно возрастающий счётчик изменений на стороне сервера. Использование меток времени в качестве курсора не допускается |
| SYN-03 | Очередь отправки хранит множество ключей изменённых сущностей. Повторные изменения одной сущности схлопываются |
| SYN-04 | Состояние сущности читается в момент отправки, а не в момент постановки в очередь |
| SYN-05 | Удаление передаётся надгробием. Физическое удаление строк в MVP не выполняется |

### 6.2 Протокол

| SYN-06 | Каждый запрос содержит номер версии протокола |
|---|---|
| SYN-07 | Отправка выполняется пачками ограниченного размера |
| SYN-08 | Пачка применяется на сервере построчно. Ответ содержит список фактически принятых ключей |
| SYN-09 | Очередь отправки очищается только по списку принятых ключей |
| SYN-10 | Применение изменений идёт в порядке: счета, места, группы, подкатегории, операции |
| SYN-11 | Клиент буферизует полученные изменения и упорядочивает их самостоятельно |
| SYN-12 | Повторная отправка не создаёт дублей за счёт вставки с обновлением по ключу |
| SYN-13 | Одно нажатие кнопки выполняет одну итерацию цикла: получение, слияние, отправка, фиксация курсора |

### 6.3 Разрешение конфликтов

| SYN-14 | Побеждает запись с более поздним `updated_at_utc`, сравнение идёт по строке целиком |
|---|---|
| SYN-15 | Удаление имеет безусловный приоритет над изменением, независимо от меток времени |
| SYN-16 | Метка времени проставляется часами клиента без коррекции |
| SYN-17 | Сервер фиксирует в журнале факт получения метки, существенно опережающей его собственное время |

### 6.4 Разделение ответственности

| SYN-18 | Слой синхронизации не проверяет доменные инварианты. Полученные строки применяются как есть |
|---|---|
| SYN-19 | Доменные инварианты проверяются исключительно при вводе данных пользователем |
| SYN-20 | Внешние ключи на таблицах сервера не создаются. Ссылочную целостность обеспечивает клиент |
| SYN-21 | Сервер не выполняет расчётов, не строит выборок по домену и не хранит производных значений |

### 6.5 Границы синхронизируемого

| SYN-22 | Синхронизируются свойства доменных сущностей, включая порядок счетов и признак «скрыть из расчётов» |
|---|---|
| SYN-23 | Не синхронизируются: последний использованный счёт, версия применённого пресета, часовой пояс, настройки соединения, тема оформления |
| SYN-24 | Перенос операций при удалении подкатегории — единственная массовая правка в системе: изменяется каждая затронутая операция, изменения уходят в очередь обычным порядком |

## 7. Стартовый набор категорий

| SEED-01 | Набор минимальный, засевается локально при первом запуске без обращения к сети |
|---|---|
| SEED-02 | Ключи категорий пресета детерминированы: UUIDv5 от фиксированного пространства имён и устойчивого текстового ключа |
| SEED-03 | Значение `updated_at_utc` у засеянных строк — фиксированная давняя метка, единая для всех устройств и версий |
| SEED-04 | Номер применённой версии пресета хранится локально. Повторное применение не выполняется никогда |
| SEED-05 | Расширение набора в новых версиях приложения не затрагивает существующие установки |
| SEED-06 | В набор входят подкатегория «Прочее» для каждой группы и две служебные подкатегории «Разница» с признаком исключения из отчётов |
| SEED-07 | Каждая категория пресета имеет заданный значок. Ключи значков фиксированы и не меняются между версиями |
| SEED-08 | Справочник мест при первом запуске пуст и наполняется по мере ввода операций |

**Обоснование SEED-02 и SEED-03.** Без детерминированных ключей второе устройство создаст дубликаты всего набора. Без фиксированной метки времени повторный засев на новом устройстве перезапишет пользовательские переименования, поскольку окажется новее их по времени.

## 9. Архитектурные решения

### 9.1 Состав проектов

В MVP создаются четыре проекта:

| Проект | Содержимое | Зависимости |
|---|---|---|
| `Finance.Domain` | Сущности, типы-значения, инварианты, доменные сервисы | Отсутствуют |
| `Finance.Application` | Слайсы функций: команда, обработчик, запросы, модель представления. Инфраструктура (доступ к данным, журналирование, уведомления) — папкой внутри | Domain |
| `Finance.App` | Приложение MAUI: страницы, навигация, ресурсы темы | Domain, Application |
| `Finance.Domain.Tests` | Тесты инвариантов и обработчиков | Domain, Application |

Обработчики, запросы и модели представления вынесены из проекта MAUI намеренно: обычная библиотека тестируется обычным xUnit, без эмулятора и без сборки под Android. В `Finance.App` остаётся только то, что без MAUI не существует.

Инфраструктура отдельным проектом не выделяется: у неё один потребитель, а шов, за которым ничего не меняется, добавляет ходы и ничего не даёт. Вынести её позже не ломает написанного.

Отложено до появления обмена с сервером:

| Проект | Содержимое | Зависимости |
|---|---|---|
| `Finance.Contracts` | Объекты передачи данных протокола, перечисления | Отсутствуют |
| `Finance.Server` | Сервер синхронизации | Contracts |

`Finance.Contracts` не будет ссылаться на `Finance.Domain`: сервер не исполняет доменную логику и не должен получать её транзитивно.

### 9.2 Организация прикладного слоя

Код режется по функциям, а не по техническим слоям: `Features/Transactions/Add`, `Features/Transactions/Edit`, `Features/Accounts/Reorder`, `Features/Balances`, `Features/Sync`. Слайс содержит команду, обработчик, модель представления и страницу.

Слайсы не ссылаются друг на друга. Запрос, потребовавшийся второму слайсу, переносится в общую инфраструктуру.

### 9.3 Работа с данными

- Доступ через фабрику контекстов, отдельный контекст на операцию.
- Пишущий путь идёт через доменные типы, читающий — напрямую в плоские модели с проекцией на стороне базы.
- Простые запросы выполняются без обёрток; составные скрываются за именованными методами.
- Доменные сущности не передаются между контекстами.

### 9.4 Команды

- Обработчики вызываются моделями представления напрямую, через интерфейсы. Посредник для диспетчеризации не применяется.
- Граница транзакции задаётся декоратором вокруг команд. Декоратор учитывает отсутствие вложенных транзакций в SQLite.
- Наполнение очереди отправки, проставление `updated_at_utc` и публикация событий изменения выполняются при сохранении.
- Засев пресета выполняется в обход автоматической установки меток времени.
- События публикуются после фиксации транзакции, несут тип изменившейся сущности и доставляются в поток интерфейса.

### 9.5 Валидация и ошибки

- Проверки формы ввода реализуются валидатором команды.
- Правила, требующие знания домена, реализуются в доменных типах.
- Нарушение инварианта выражается доменным исключением специального типа и обрабатывается глобально.
- Межтабличные инварианты реализуются доменным сервисом, принимающим операцию и связанные счета.

### 9.6 Создание и восстановление сущностей

Конструкторы доменных типов закрыты. Создание выполняется фабричным методом с полной проверкой. Восстановление из хранилища идёт отдельным путём без проверок. Путь восстановления публичный: ограничивать его видимость не нужно. Его XML-комментарий обязан прямо говорить, что метод не проверяет инварианты и предназначен только для чтения из хранилища.

## 11. План реализации

### Этап 0. Доменное ядро

**Цель.** Получить проверенную доменную модель до появления инфраструктуры.

**Состав.**
- Структура решения, пять проектов, зависимости между ними.
- Типы-значения: денежная сумма с валютой, запрет сложения разных валют.
- Сущности с закрытыми конструкторами, фабричными методами и путём восстановления.
- Реализация инвариантов INV-01 — INV-21.
- Доменный сервис межтабличных проверок.
- Тесты на все инварианты.

**Критерии готовности.** Каждый инвариант покрыт тестом на срабатывание и на пропуск корректного значения. Доменный проект не имеет внешних зависимостей.

**Замечание.** Это единственный этап, где исчерпывающее покрытие тестами достижимо и дёшево. Его стоит довести до конца.

---

### Этап 1. Локальное приложение

**Цель.** Работающее приложение без сети, пригодное для ежедневного использования.

**Состав.**
- Схема базы, миграции, резервное копирование перед миграцией.
- Контекст с фабрикой, предкомпилированная модель, режим журналирования.
- Переопределение сохранения: метки изменения, очередь отправки, события.
- Засев пресета с детерминированными ключами и фиксированной меткой.
- Слайсы: создание, редактирование, удаление операции; создание и редактирование счёта; управление категориями; порядок счетов.
- Запросы балансов и ленты.
- Экраны: балансы, лента, форма операции, списки счетов и категорий, настройки.
- Навигация с типизированной обёрткой.

**Критерии готовности.** Полный цикл ввода трёх видов операций. Балансы корректны при смешанных валютах и переводах между ними. Лента упорядочена согласно FR-LED-02. Приложение установлено на телефон и используется по назначению.

**Замечание.** Очередь отправки и надгробия реализуются на этом этапе, хотя используются только на следующем. Их добавление позже потребует ретроспективного заполнения.

---

### Этап 2. Синхронизация

**Цель.** Обмен данными между устройством и сервером.

**Состав.**
- Объекты передачи данных протокола, номер версии.
- Сервер: схема без внешних ключей, счётчик изменений, эндпоинты получения и отправки, проверка токена, структурная валидация.
- Клиент: формирование пачки в топологическом порядке, отправка, обработка списка принятых ключей, очистка очереди, продвижение курсора.
- Применение полученных изменений с буферизацией и упорядочиванием.
- Слияние по правилам SYN-14 и SYN-15.
- Экран состояния синхронизации.

**Критерии готовности.** Полная выгрузка накопленных за первый этап данных проходит без потерь. Повторный запуск не создаёт дублей. Обрыв связи посреди отправки не приводит к расхождению.

**Замечание.** Наиболее трудоёмкий и наименее предсказуемый по срокам этап. Оценка требует запаса.

---

### Этап 3. Второе устройство

**Цель.** Подтвердить корректность слияния на реальных конфликтах.

**Состав.** Прогон сценариев с оформлением каждого в виде теста:

1. Одна операция изменена на двух устройствах в автономном режиме.
2. Операция удалена на одном устройстве и изменена на другом.
3. Категория пресета удалена, приложение установлено на новое устройство.
4. Категория пресета переименована, приложение установлено на новое устройство.
5. Обрыв связи в середине отправки пачки с последующей повторной отправкой.
6. Часы одного устройства сдвинуты вперёд относительно другого.

**Критерии готовности.** Все сценарии дают детерминированный результат, совпадающий на обоих устройствах.

**Замечание.** Сценарии 3 и 4 проверяют конструкцию SEED-02 — SEED-04 целиком.

---

### Этап 4. Развитие

Порядок определяется по результатам эксплуатации. Ориентировочная последовательность по соотношению ценности и стоимости:

| Функция | Основание |
|---|---|
| Отчёт о расходах по категориям за период | Основная ценность продукта, схема готова |
| Выгрузка данных в файл | Страховка от потери устройства |
| Автоматический запуск синхронизации | Устранение ручного действия |
| Внешняя аутентификация | Требует добавления владельца строк в таблицы сервера |
| Поиск и фильтры по операциям | Растёт в ценности с объёмом истории |
| Чистка надгробий и полная пересинхронизация | Требуется при длительной эксплуатации нескольких устройств |
| Сверка контрольной суммой | Диагностика расхождений |
| Блокировка приложения | По потребности |

| Аналитика | Схема готова. Требует решения о сворачивании подкатегорий в группы |
| Импорт | Поле внешнего идентификатора зарезервировано. Требует пакетной отправки при первой синхронизации |
| Поддержка iOS | Выбранная платформа не создаёт препятствий |

**Не подлежит отложению.** Схема идентификаторов и детерминированные ключи пресета. Изменение после накопления данных возможно только полной миграцией с перепрошивкой всех ссылок.

## 13. Риски

| Риск | Оценка | Смягчение |
|---|---|---|
| Отсутствие отчётов в MVP снижает мотивацию довести проект до третьего этапа | Высокая вероятность, высокий ущерб | Реализовать один отчёт о расходах по категориям в конце первого этапа |
| Отсутствие выгрузки данных при единственном устройстве | Средняя вероятность, высокий ущерб | Резервное копирование перед миграцией закрывает часть риска. Полностью закрывается выгрузкой в файл |
| Недооценка трудоёмкости второго этапа | Высокая вероятность, средний ущерб | Закладывать запас, не планировать на этап фиксированный срок |
| Расхождение данных между устройствами без внешних признаков | Средняя вероятность, высокий ущерб | Сценарные тесты третьего этапа, сверка контрольной суммой в дальнейшем |
| Отставание версии MAUI от релиза платформы | Средняя вероятность, низкий ущерб | Проверить доступность всей связки до начала работ |
| Изменение требований внешних провайдеров аутентификации | Высокая вероятность, низкий ущерб | Сверяться с актуальной документацией на момент реализации |
