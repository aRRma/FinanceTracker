# Деньги хранятся целыми копейками

В SQLite денежная колонка объявлена как `INTEGER` и хранит копейки: 1234,56 ₽ лежит числом 123456. Перевод в обе стороны выполняет один конвертер, весь остальной код работает с `Money` и `decimal` и о копейках не знает.

**Хранение `decimal` как есть** отвергнуто: у SQLite нет типа с фиксированной точностью, и провайдер по умолчанию кладёт `decimal` в TEXT. По тексту не работают ни `SUM`, ни сравнение — баланс пришлось бы считать в памяти, подняв всю ленту, а это ровно то, что запрещено NFR-02, и то, что не укладывается в 300 мс при расчётном объёме данных (NFR-01).

**Числа с плавающей точкой** отвергнуты требованием NFR-09: это та самая ошибка, ради которой в домене заведён `Money`.

Предел суммы — 999 999 999 999,99, то есть 99 999 999 999 999 копеек; до предела 64-битного целого остаётся ещё около пяти порядков. Переполнение достижимо только в `SUM` по ленте, и для него понадобилось бы порядка 92 000 операций подряд по 999 млрд ₽ каждая при расчётном объёме в 100 000 операций за весь срок (SYS-06). SQLite при переполнении не обрезает молча, а возвращает ошибку.

Осознанная цена: число в дампе базы читается не сразу — 123456 вместо 1234.56. Взамен `SUM` по колонке точен, сортировка по сумме верна, а округление остаётся там, где ему место, — в форме ввода.

Решение из необратимых: после накопления данных смена формата потребует полной миграции с пересчётом всех сумм.
