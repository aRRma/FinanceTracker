# Архитектурные решения и стек

Состав проектов, организация прикладного слоя, работа с данными, выбор технологий. Идентификаторы: `TECH-*`.

## Состав проектов

В MVP создаются шесть проектов:

| Проект | Содержимое | Целевой фреймворк | Зависимости |
|---|---|---|---|
| `Finance.Domain` | Сущности, типы-значения, инварианты, доменные сервисы | `net10.0` | Отсутствуют |
| `Finance.Application` | Слайсы функций: команда, обработчик, запросы, модель представления. Инфраструктура (доступ к данным, журналирование, уведомления) — папкой внутри | `net10.0` | Domain |
| `Finance.App` | Приложение MAUI: страницы, навигация, ресурсы темы | `net10.0-android`, `SupportedOSPlatformVersion` = 36 (SYS-01) | Domain, Application |
| `Finance.Domain.Tests` | Тесты доменных правил: срабатывание каждого и пропуск корректного значения | `net10.0` | Domain, Application |
| `Finance.Application.Tests` | Тесты обработчиков, запросов и моделей представления на настоящей базе SQLite во временной папке | `net10.0` | Domain, Application |
| `Finance.Docs.Tests` | Проверки стартового набора и документации | `net10.0` | Domain и Application — ради той же реализации UUIDv5 и того же разбора стартового набора, которыми пользуется инициализация базы. Документы и данные читает как файлы |

Обработчики, запросы и модели представления вынесены из проекта MAUI намеренно: обычная библиотека тестируется обычным xUnit, без эмулятора и без сборки под Android. В `Finance.App` остаётся только то, что без MAUI не существует.

Внутри доменного проекта пять папок, и пространство имён совпадает с папкой: `Entities` — сущности с их инвариантами, `Enums` — перечисления предметной области, `Values` — денежная сумма и генерация ключей, `Rules` — проверки, которым нужны соседние записи или общие границы, `Errors` — каталог правил, исключение и сборка его текста. Каталог правил `Invariant` лежит в `Errors`, а не в `Enums`: он читается только вместе с исключением, которое его бросает. Там же лежат сами тексты: `RuleTexts.resx` со словами и `RuleText` с ключами к ним — домен собирает сообщение сам, но в коде его не хранит.

Инфраструктура отдельным проектом не выделяется: у неё один потребитель, а шов, за которым ничего не меняется, добавляет ходы и ничего не даёт. Вынести её позже не ломает написанного.

Отложено до появления обмена с сервером:

| Проект | Содержимое | Зависимости |
|---|---|---|
| `Finance.Contracts` | Объекты передачи данных протокола, перечисления | Отсутствуют |
| `Finance.Server` | Сервер синхронизации | Contracts |

`Finance.Contracts` не будет ссылаться на `Finance.Domain`: сервер не исполняет доменную логику и не должен получать её транзитивно.

## Организация прикладного слоя

Код режется по функциям, а не по техническим слоям: `Features/<Функция>[/<Экран>]`, например `Features/Transactions/Card`, `Features/Accounts/Catalog`, `Features/Report`; полный состав виден по папкам. `Features/WalletImport` — разовый перенос истории из Wallet ([ADR-0014](adr/0014-wallet-import-one-shot-through-domain-path.md)); у его строки на экране «О программе» своя модель, чтобы слайс «О программе» на него не ссылался. Слайс содержит команду, обработчик, запросы и модель представления; страница живёт в `Finance.App`. Запись и правка одной сущности — один слайс `Card`: экран у них один, а отличает их только заполненный ключ.

Слайсы не ссылаются друг на друга. Запрос, потребовавшийся второму слайсу, переносится в общую инфраструктуру.

Текста в слайсах нет: подписи, заголовки и сообщения лежат в `Texts/UiTexts.resx` — одном файле на всё приложение, потому что одни и те же слова показывают и разметка, и модель представления. Язык приходит параметром `AddFinance` и хранится в `UiCulture`; форматы даты собраны в `DateText`, формат суммы — в `MoneyFormat`. Подробности решения — [ADR-0012](adr/0012-text-in-resources-culture-as-parameter.md).

## Работа с данными

- Доступ через фабрику контекстов, отдельный контекст на операцию.
- Пишущий путь идёт через доменные типы, читающий — напрямую в плоские модели с проекцией на стороне базы.
- Простые запросы выполняются без обёрток; составные скрываются за именованными методами.
- Доменные сущности не передаются между контекстами.

## Команды

- Обработчики вызываются моделями представления напрямую, через интерфейсы. Посредник для диспетчеризации не применяется.
- Граница транзакции задаётся типом `UnitOfWork`: обработчик передаёт ему тело команды, а не открывает транзакцию сам. Вложенности нет — её нет и в SQLite: команда получает свой контекст и свою транзакцию, а обработчики друг друга не вызывают.
- `updated_at_utc` проставляется при сохранении, в переопределении `SaveChanges`; очередь отправки будет наполняться там же, когда появится обмен. Инициализация базы идёт в обход.
- События изменения публикует `UnitOfWork` после фиксации транзакции: они несут тип изменившейся сущности и доставляются в поток интерфейса, где их принимает `ScreenViewModel`.

## Валидация и ошибки

- Проверки формы ввода — незаполненное поле, недобранная сумма — живут в модели представления: она же показывает сообщение и подводит к нему экран.
- Правила, требующие знания домена, реализуются в доменных типах.
- Нарушение инварианта выражается доменным исключением специального типа. Ловит его модель представления карточки и показывает текст правила на самом экране: глобальный перехват сказал бы о нарушении, но не показал бы, какое поле править. Что не поймала карточка, показывает `Guarded`: пользователю — только текст `DomainException` и `DatabaseMigrationException`, остальное — общим сообщением и в журнал.
- Межтабличные инварианты проверяют статические правила домена (`TransactionRules`, `CategoryRules`, `NameUniqueness`): прочитанные данные подаются параметром, решение остаётся за доменом.

## Создание и восстановление сущностей

Конструкторы доменных типов закрыты. Создание выполняется фабричным методом с полной проверкой. Восстановление из хранилища идёт отдельным путём без проверок. Путь восстановления публичный: ограничивать его видимость не нужно. Его XML-комментарий обязан прямо говорить, что метод не проверяет инварианты и предназначен только для чтения из хранилища.

## Особенности реализации

| TECH-01 | Идентификаторы хранятся в SQLite текстом в каноническом представлении. Двоичное представление .NET имеет платформозависимый порядок байтов и ломает сортировку ленты и локальность вставок (ADR-0002) |
|---|---|
| TECH-02 | Предкомпилированная модель не применяется: EF отказывается её собирать, пока у таблиц есть глобальный фильтр мягкого удаления, а фильтр важнее — без него забытое в одном запросе отсечение показало бы удалённые записи, и заметили бы это не сразу. Модель из пяти таблиц строится при первом обращении к базе |
| TECH-03 | Корректность работы проверяется на релизной сборке: отсечение неиспользуемого кода влияет на механизмы, использующие отражение |
| ~~TECH-04~~ | Отложено вместе с обменом: при разработке эмулятор обращается к хосту по служебному адресу, для незашифрованного соединения нужна отладочная конфигурация сетевой безопасности |
| ~~TECH-05~~ | Отложено вместе с обменом: в эксплуатации перед сервисом ставится обратный прокси с автоматическим получением сертификата |
| TECH-06 | Тема оформления и версия приложения приходят в прикладной слой снаружи, параметрами сборки служб: что такое тёмное оформление окна и где лежит манифест, знает только MAUI. Тема применяется через тот же переход в поток интерфейса, что и оповещение об изменении данных — подготовка приложения идёт в фоновом потоке |
| TECH-07 | Номер схемы базы для экрана «О программе» — число накатанных миграций, прочитанное у самой базы. Отдельный счётчик версии схемы не заводится: он разошёлся бы с фактическим состоянием базы при первой же забытой правке |
| TECH-08 | Суммы отчёта база отдаёт порознь на каждый вид операции, а со знаком их сводит прикладной слой: `SUM` со знаком внутри `CASE` потерял бы конвертер копеек — он применяется к колонке, а не к выражению. Порядок строк поэтому считается по сведённому итогу, а не `ORDER BY` в базе (ADR-0013) |
| TECH-09 | Релиз компилируется полным AOT, а не профильным: по умолчанию заранее компилируется только стартовый профиль шаблонного приложения MAUI, а EF Core и собственный код компилируются JIT при каждом запуске. Холодный старт вдвое короче ценой APK в полтора раза больше; замер с датой — в комментарии `Finance.App.csproj`. Настройка относится к Mono: в .NET 11 Android переходит на CoreCLR, и её заменяет `MauiEnableFullReadyToRun` с новым замером (пункт в PLAN.md). NativeAOT на Android экспериментальный; EF Core под ним требует предкомпилированную модель, а её не даёт фильтр мягкого удаления (TECH-02). Вшитый JSON (стартовый набор, набор значков) разбирается генератором исходного кода, а не отражением |
| TECH-10 | Момент времени лежит в SQLite `TEXT` фиксированной длины с нулевым смещением через один конвертер. Поставщик отказывается сортировать по `DateTimeOffset` (смещения могли бы различаться), а ленте нужна сортировка по `created_at_utc`; одинаковая длина и смещение делают порядок текста порядком времени |
| TECH-11 | Перед миграцией схемы снимается резервная копия базы через `VACUUM INTO`, при неудачной миграции база откатывается на неё. Хранится одна последняя копия |
| TECH-12 | Возврат настройки к системному значению — удаление строки, а не запись слова «системный»: записанное значение часового пояса не переехало бы вместе с пользователем. Тема — исключение: системная тема записывается, иначе её не отличить от первого запуска |
| TECH-13 | Время читается только через `IClock`: прямой `DateTimeOffset.UtcNow` или `DateTime.Now` обходит зону пользователя и тестовые часы. `SystemClock` берёт момент у `TimeProvider`, тесты подставляют `TestTime`; правило сверяет тест `Время_читается_только_через_часы_приложения` |
