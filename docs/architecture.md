# Архитектурные решения и стек

Состав проектов, организация прикладного слоя, работа с данными, выбор технологий. Идентификаторы: `TECH-*`.

## Состав проектов

Решение состоит из семи проектов:

| Проект | Содержимое | Целевой фреймворк | Зависимости |
|---|---|---|---|
| `Finance.Domain` | Сущности, типы-значения, инварианты, правила (`Rules`) | `net10.0` | Отсутствуют |
| `Finance.Application` | Слайсы функций: команда, обработчик, запросы, модель представления. Инфраструктура (доступ к данным, часы, настройки, уведомления об изменении, диагностика) — папкой внутри | `net10.0` | Domain |
| `Finance.App` | Приложение MAUI: страницы, контролы, навигация, ресурсы темы, платформенная часть Android | `net10.0-android`, `SupportedOSPlatformVersion` = 36 (SYS-01) | Domain, Application |
| `Finance.Import` | Перенос истории из других приложений, сейчас — из Wallet. Работает на рабочей машине: приложение на него не ссылается ([ADR-0014](adr/0014-wallet-import-one-shot-through-domain-path.md)) | `net10.0` | Domain, Application — с доступом к внутренностям: пишет историю одной транзакцией через доменные фабрики |
| `Finance.Domain.Tests` | Тесты доменных правил: срабатывание каждого и пропуск корректного значения | `net10.0` | Domain |
| `Finance.Application.Tests` | Тесты обработчиков, запросов и моделей представления на настоящей базе SQLite во временной папке; сверка с моделью на случайных данных; тесты переноса | `net10.0` | Domain, Application, Import |
| `Finance.Docs.Tests` | Проверки стартового набора, документации и соглашений по исходникам: запечатанные классы, часы, обработчики событий, тексты, контраст, знак приложения | `net10.0` | Domain и Application — ради той же реализации UUIDv5 и того же разбора стартового набора. Документы, данные и исходники читает как файлы |

Обработчики, запросы и модели представления вынесены из проекта MAUI намеренно: обычная библиотека тестируется обычным xUnit, без эмулятора. В `Finance.App` остаётся только то, что без MAUI не существует.

Внутри доменного проекта пять папок, и пространство имён совпадает с папкой: `Entities` — сущности с их инвариантами, `Enums` — перечисления предметной области, `Values` — денежная сумма и генерация ключей, `Rules` — проверки, которым нужны соседние записи или общие границы, `Errors` — каталог правил `Invariant`, исключение и тексты нарушений (`RuleTexts.resx` и ключи к нему `RuleText`). Каталог правил лежит в `Errors`, а не в `Enums`: он читается только вместе с исключением, которое его бросает.

Инфраструктура отдельным проектом не выделяется — [ADR-0008](adr/0008-vertical-slices-outside-maui-no-mediator.md). Проекты `Finance.Contracts` и `Finance.Server` появятся вместе с обменом ([ADR-0007](adr/0007-mvp-single-device-dumb-server.md)); `Contracts` не будет ссылаться на `Domain`: сервер не исполняет доменную логику.

## Организация прикладного слоя

Код режется по функциям, а не по техническим слоям: `Features/<Функция>[/<Экран>]`, например `Features/Transactions/Card`, `Features/Accounts/Catalog`, `Features/Report`; полный состав виден по папкам. Слайс содержит команду, обработчик, запросы и модель представления; страница живёт в `Finance.App`. Запись и правка одной сущности — один слайс `Card`: экран у них один, а отличает их только заполненный ключ.

Слайсы не ссылаются друг на друга. Запрос или обработчик, потребовавшийся второму слайсу, переносится в общую инфраструктуру: так удаление операций (`Infrastructure/Deletion`) общее у формы операции и ленты — и текст подтверждения у них один.

Текста в слайсах нет: он лежит в `Texts/UiTexts.resx` — одном файле на всё приложение; названия значков для озвучки — в `Texts/IconNames.resx`, города списка часовых поясов — в `Texts/CityNames.resx`. Язык приходит параметром `AddFinance` и хранится в `UiCulture`; форматы даты — в `DateText`, суммы — в `MoneyFormat`. Причины — [ADR-0012](adr/0012-text-in-resources-culture-as-parameter.md).

## Работа с данными

- Доступ через фабрику контекстов, отдельный контекст на операцию.
- Пишущий путь идёт через доменные типы, читающий — напрямую в плоские модели с проекцией на стороне базы.
- Простые запросы выполняются без обёрток; составные скрываются за именованными методами.
- Доменные сущности не передаются между контекстами.

## Команды

- Обработчики вызываются моделями представления напрямую, через интерфейсы. Посредник для диспетчеризации не применяется.
- Граница транзакции задаётся типом `UnitOfWork`: обработчик передаёт ему тело команды, а не открывает транзакцию сам. Вложенности нет — её нет и в SQLite: команда получает свой контекст и свою транзакцию, а обработчики друг друга не вызывают.
- `updated_at_utc` проставляется при сохранении, в переопределении `SaveChanges`; очередь отправки будет наполняться там же, когда появится обмен. Инициализация базы идёт в обход.
- События изменения (`DataChange`) публикует `UnitOfWork` после фиксации транзакции; настройки, которые пишутся без транзакции (тема, часовой пояс), и возврат из фона со сменой пояса публикуют их сами. Счёт по умолчанию зависит от данных и пишется через `UnitOfWork`. События доставляются в поток интерфейса, где их принимает `ScreenViewModel`.

## Валидация и ошибки

- Проверки формы ввода — незаполненное поле, недобранная сумма — живут в модели представления: она же показывает сообщение и подводит к нему экран.
- Правила, требующие знания домена, реализуются в доменных типах.
- Нарушение инварианта выражается доменным исключением специального типа. Ловит его модель представления карточки и показывает текст правила на самом экране: глобальный перехват сказал бы о нарушении, но не показал бы, какое поле править. Что не поймала карточка, показывает `Guarded`: пользователю — только текст `DomainException` и `DatabaseMigrationException`, остальное — общим сообщением и в журнал.
- Межтабличные инварианты проверяют статические правила домена (`TransactionRules`, `CategoryRules`, `NameUniqueness`): прочитанные данные подаются параметром, решение остаётся за доменом.

## Создание и восстановление сущностей

Конструкторы доменных типов закрыты. Создание выполняется фабричным методом с полной проверкой. Восстановление из хранилища идёт отдельным путём без проверок. Путь восстановления публичный: ограничивать его видимость не нужно. Его XML-комментарий обязан прямо говорить, что метод не проверяет инварианты и предназначен только для чтения из хранилища.

## Миграции схемы

Номер схемы на экране «О программе» — число накатанных миграций (TECH-07). Перед каждой — резервная копия (NFR-06, NFR-26).

| № | Миграция | Что меняет |
|---|---|---|
| 1 | `Initial` | Схема MVP |
| 2 | `LedgerFeedIndex` | Индекс общей ленты без счёта (NFR-04) |
| 3 | `AcceptsAnyKind` | Признак универсальной группы, расходные группы набора — универсальные (ADR-0013) |
| 4 | `MergeServiceGroups` | Одна служебная группа вместо двух, операции переезжают (ADR-0013) |
| 5 | `AddUnsortedGroups` | Группы «Без категории» в установленных базах (SEED-10) |
| 6 | `AddAccountColorAndIcon` | Цвет и значок счёта, цвета уже заведённым счетам (ADR-0016) |
| 7 | `ForgetLastAccount` | Удаляет настройку последнего использованного счёта (FR-SET-07) |

## Особенности реализации

| Код | Особенность |
|---|---|
| TECH-01 | Идентификаторы хранятся в SQLite текстом в каноническом представлении (ADR-0002) |
| TECH-02 | Предкомпилированная модель не применяется: EF отказывается её собирать, пока у таблиц сущностей есть глобальный фильтр мягкого удаления, а фильтр важнее — без него забытое в одном запросе отсечение показало бы удалённые записи, и заметили бы это не сразу. Модель строится при первом обращении к базе |
| TECH-03 | Корректность работы проверяется на релизной сборке: отсечение неиспользуемого кода влияет на механизмы, использующие отражение |
| ~~TECH-04~~ | Отложено вместе с обменом: при разработке эмулятор обращается к хосту по служебному адресу, для незашифрованного соединения нужна отладочная конфигурация сетевой безопасности |
| ~~TECH-05~~ | Отложено вместе с обменом: в эксплуатации перед сервисом ставится обратный прокси с автоматическим получением сертификата |
| TECH-06 | Тема оформления и версия приложения приходят в прикладной слой снаружи, параметрами сборки служб: что такое тёмное оформление окна и где лежит манифест, знает только MAUI. Тема применяется через тот же переход в поток интерфейса, что и оповещение об изменении данных — подготовка приложения идёт в фоновом потоке |
| TECH-07 | Номер схемы базы для экрана «О программе» — число накатанных миграций, прочитанное у самой базы. Отдельный счётчик версии схемы разошёлся бы с фактическим состоянием базы при первой же забытой правке |
| TECH-08 | Суммы отчёта база отдаёт порознь на каждый вид операции, а со знаком их сводит прикладной слой. Порядок строк поэтому считается по сведённому итогу, а не `ORDER BY` в базе (ADR-0013) |
| TECH-09 | Релиз компилируется полным AOT, а не профильным: по умолчанию заранее компилируется только стартовый профиль шаблонного приложения MAUI, а EF Core и собственный код компилируются JIT при каждом запуске. Холодный старт вдвое короче ценой APK в полтора раза больше; замер с датой — в комментарии `Finance.App.csproj`. NativeAOT на Android экспериментальный, а EF Core под ним требует предкомпилированную модель (TECH-02) |
| TECH-10 | Момент времени лежит в SQLite `TEXT` фиксированной длины с нулевым смещением через один конвертер. Поставщик отказывается сортировать по `DateTimeOffset`, а ленте нужна сортировка по `created_at_utc`; одинаковая длина и смещение делают порядок текста порядком времени |
| TECH-11 | Резервная копия перед миграцией снимается `VACUUM INTO` (NFR-06, NFR-26) |
| TECH-12 | Возврат настройки к системному значению — удаление строки, а не запись слова «системный»: записанное значение часового пояса не переехало бы вместе с пользователем. Тема — исключение: системная тема записывается, иначе её не отличить от первого запуска |
| TECH-13 | Время читается только через `IClock`: прямой `DateTimeOffset.UtcNow` или `DateTime.Now` обходит зону пользователя и тестовые часы. `SystemClock` берёт момент у `TimeProvider`, тесты подставляют `TestTime`; правило сверяет `Время_читается_только_через_часы_приложения`. Исключение — диагностика (`CrashReports`, `ActionTrail`): она создаётся раньше контейнера служб и берёт время у `TimeProvider` напрямую (TECH-20) |
| TECH-14 | Индексы операций частичные — по неудалённым строкам, фильтром `deleted_at_utc IS NULL`, тем же предикатом, что глобальный фильтр EF добавляет к каждому запросу: без фильтра индекс хранил бы и надгробия. Новый индекс заводится по плану запроса, показавшему полный проход, а не впрок: `CREATE INDEX` в SQLite дёшев на любой стадии |
| TECH-15 | Восстановление из выгрузки — не откат на резервную копию, их легко спутать: выгрузка снимается тем же `VacuumInto`, но в папку временных файлов (`DatabaseLocation.CacheFolder`), иначе слот резервной копии затёрла бы следующая миграция. Порядок и причины — ADR-0015 |
| TECH-16 | Знак счёта рисует один контрол `AccountBadge` в трёх размерах, значок выбирает один маппинг `AccountIcon.For`, в коде чтения счёт со знаком — запись `AccountMark`. Заливка — токен темы `Account{Цвет}Light`/`Dark`, привязанный к теме платформой; цвет значка на заливке — по `AccountColors.TakesDarkGlyph`, тем же правилом пользуется `ContrastTests` (ADR-0016). Подпись строки общей ленты собирает контрол `FeedCaption`: ячейки ленты переиспользуются, и колонки задаются кодом на каждую смену строки |
| TECH-17 | Лента дочитывается курсором ленты — датой, `created_at_utc` и ключом последней показанной строки (`FeedCursor`), а не пропуском строк: `OFFSET` база проходит заново на каждой странице, а курсор ищет с места по тому же индексу, что задаёт порядок, и не повторяет строку, записанную между страницами. Перечитывание после правки читает всю дочитанную глубину одним запросом — так сохраняется место прокрутки |
| TECH-18 | Счёт по умолчанию вычисляется при чтении, а не поддерживается записью: в настройке лежит только явный выбор, а `DefaultAccount.Resolve` отдаёт его, пока счёт не заблокирован и не удалён, иначе — первый незаблокированный в порядке экрана «Счета». Так первый заведённый счёт становится счётом по умолчанию без кода в заведении счёта, а старая база или выгрузка не требует миграции. Блокировка и удаление выбранного стирают выбор в своей транзакции: иначе разблокированный счёт молча вернул бы себе роль; по той же причине выбор пишется только на незаблокированный счёт, проверкой в той же транзакции. Форма, подтверждение карточки и строка «Ещё» читают кандидатов в одном порядке и называют один счёт |
| TECH-19 | Защита входа (ADR-0017) хранится вне базы: след ПИН-кода — в `SecureStorage`, признак, счёт попыток и пауза — в `Preferences`, через `IPinStore` и `IDevicePreferences` от платформы. Заслонка — полноэкранный `Dialog` поверх активности (`LockCover`) с содержимым MAUI (`LockCoverView`), а не страница `Shell`, иначе осталась бы под открытым вопросом. Подъём: при запуске — в `OnCreate`, при возврате — в `OnRestart` после пяти минут в фоне, страховкой — в `OnResume`; запуском считается только первое создание активности за жизнь процесса. `OnStop` закрывает содержимое окна приложения шторкой, чтобы первым кадром возврата были не балансы. Содержимое заслонки создаётся при каждом подъёме: у чужого окна нет родителя, и смена темы до него не дошла бы. Окно прозрачно с самого начала (`Format.Translucent`): формат, сменённый на ходу, пересоздал бы поверхность, и растворение после входа (`LockCover.LeaveAsync`) мигнуло бы. Отступы под системные полосы в окне заслонки ставит `LockCoverView.Inset`. Признак миниатюры в недавних обновляется в `OnResume` и `OnPause`. Время в фоне — `SystemClock.ElapsedRealtime` через `IUptime` |
| TECH-20 | Отчёты о сбоях (ADR-0018) — файл в папке данных приложения и один предыдущий. `CrashReports` создаёт платформа в `MainApplication.OnCreate` до сборки служб (`CrashCatcher`) и передаёт в `AddFinance` готовыми: у записи и экрана один файл и одна блокировка. Запись синхронная, со сбросом на диск: процесс умирает сразу за обработчиком. Источники — необработанные исключения .NET в любом потоке, свой обработчик Java перед обработчиком среды, забытые задачи (предупреждение), `Guarded` и сорванная миграция в `DataPage`; одно падение проходит до трёх обработчиков, пишет первый. Текст исключения — только у белого списка `CrashDescription`. След действий (`ActionTrail`) живёт в памяти; экран и последнее действие уходят системе сводкой `setProcessStateSummary`. При запуске `PastExits` разбирает `GetHistoricalProcessExitReasons` новее запомненной метки, пропускает обычные завершения и уже записанные падения; из трассы нативного падения (`ProtoReader`) берутся сигнал и кадры упавшего потока, из трассы зависания — стек главного потока. Экраны читают файл, не дожидаясь базы (`DataPage.ReadsDatabase`); вид сбоя (`CrashCategory`) и экран (`CrashScreens`) выводятся при показе, формат файла не меняется. Выбранный отчёт переходит на свой экран через `CrashReportChoice`: ключа у отчёта нет |
| TECH-21 | Счета отчёта (FR-RPT-12) — `ReportAccounts`: правило «все активные счета валюты» или список ключей. Правило, а не список, — чтобы новый счёт входил сам. Выбор держит `ReportChoice` в памяти до перезапуска: отчёт по одному вкладу через неделю легко принять за обычный. Каждое чтение `IReportQuery` получает набор параметром, три уровня считают по одному набору. «Все активные» — тот же предикат `CountedAccounts`, что итог дня; выбранные руками ключи сверяются и по валюте, иначе счёт, сменивший валюту, смешал бы их. Доменного правила на одну валюту нет: набор не хранит ни одна сущность, смешение исключают экран и `Money` |
| TECH-22 | Подготовка приложения (`FinanceStartup.PrepareAsync`) — одна задача на запуск, общая для всех вкладок: файл базы с копией и миграциями, стартовый набор при первом запуске, сохранённый часовой пояс, тема. Запоминается только удавшаяся подготовка: разовая помеха вроде нехватки места не должна держать приложение закрытым до переустановки. Незнакомый сохранённый пояс запуску не мешает — берётся системный |
