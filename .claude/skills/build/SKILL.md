# Команды, сборка и публикация

```
dotnet build Finance.slnx -v q                  # всё решение, включая Finance.App
python tools/build_prototype.py                 # пересобрать прототип из макетов — после КАЖДОЙ правки mockups.html
```

Команды запуска тестов и чтение их вывода — в навыке `tests`.

**Файловые приложения C#** (`dotnet путь.cs`, `dotnet run -`) — замеры на SDK 10.0.401:

- `#:property PublishAot=false` — в каждом скрипте, включая `dotnet run -`. Без него рефлексия (`JsonSerializer` без генератора) в `tools/` роняет сборку ошибками IL2026/IL3050 — туда доходит `TreatWarningsAsErrors` из `Directory.Build.props`, — а вне репозитория собирается и падает уже при запуске: «Reflection-based serialization has been disabled».
- С `#:include` первая строка — `#!/usr/bin/env dotnet`, иначе CA2266.
- `#:project` на `Finance.Application` поднимает каждый запуск с 0,3 до 1,1 с: MSBuild каждый раз сверяет ссылку. Для часто зовущихся скриптов — `#:package` с той же версией, что в проекте.
- `#:sdk Microsoft.NET.Sdk.Web` запускает скрипт в его собственной папке: относительный путь `docs/ui` ищется в `tools/`. Лечится `#:property RunWorkingDirectory=$(MSBuildStartupDirectory)`. Обычный SDK работает в папке запуска.
- Первый запуск после правки — 2–3 с на сборку, дальше около 0,3 с; кэш — в `%TEMP%\dotnet\runfile`, в папке скрипта `bin` и `obj` не появляются. `dotnet build путь.cs` проверяет компиляцию без запуска.

Сборщик прототипа пока на Python (до переписывания на C#): на Windows команда называется `python`, `python3` там — заглушка Microsoft Store.

Запись файла через heredoc (`cat > файл <<EOF`) запрещена: в Git Bash на Windows кириллица и кавычки ломают разбор, а кодировка зависит от кодовой страницы. Новый файл пишется целиком, существующий правится точечной заменой. **Массовая правка нескольких мест сразу — C#-скрипт, записанный инструментом Write во временную папку сессии и запущенный `dotnet путь.cs -- аргументы`.** Кириллица в искомых строках и в выводе проходит без настроек (проверено из Git Bash); скрипт вне репозитория не подхватывает его `Directory.Build.props`, и предупреждения не роняют сборку. Первой строкой — `#:property PublishAot=false`: иначе рефлексия (`JsonSerializer` без генератора) падает уже при запуске. Где правка в одном-двух местах — инструмент Edit, а не скрипт.

Скрипт, идущий по существующим файлам, читает и пишет их байтами: метка BOM определяется по первым трём байтам и возвращается на место, а конец строки берётся из самого файла (`text.Contains("\r\n") ? "\r\n" : "\n"`). **Вопреки `core.autocrlf=true`, в рабочем дереве подавляющее большинство файлов лежит с LF** — 305 против 41 на сентябрь 2026: шаблон, набранный с `\r\n`, не найдётся ни в одном из них, и правка выглядит как «шаблон не найден». Запись с `\n` поверх файла с CRLF переписывает его целиком: правка на две строки приходит в отличиях как файл, изменённый весь.

**Скрипт массовой правки пишется идемпотентным:** `if (count == 0 && text.Contains(replacement)) continue;`. Он почти наверняка упадёт на середине списка — шаблон в очередном файле окажется другим, — а записанные до падения файлы останутся правлеными, и повторный запуск сообщит о них «0 matches». Без этой строки после каждой поправки приходится вручную вырезать из скрипта уже сделанное.

`git add` и `git commit` печатают по строке `LF will be replaced by CRLF` на каждый файл (`core.autocrlf=true`, `.gitattributes` нет): полсотни строк шума вместо результата. Из PowerShell хвост фильтруется `| Select-String -NotMatch "LF will be"`.

Многострочное сообщение коммита пишется **из PowerShell** here-string `@'…'@`, закрывающая метка — в нулевой колонке. Та же конструкция в Bash уедет в сообщение буквально: заголовком станет `@`, а правка задним числом потребует принудительной отправки.

**Ловушки сборки.**

- Решение — `Finance.slnx`, не `.sln`: `dotnet new sln` в .NET 10 создаёт новый формат, и `dotnet sln Finance.sln add` молча не находит файл.
- `dotnet build` принимает ровно один проект: два пути подряд дают `MSB1008`. Для нескольких — по решению целиком.
- `TreatWarningsAsErrors` включён. Чаще всего ломают `CS1573` (описан `<param>` не у всех параметров — описывай либо все, либо ни одного) и `CS1718` (сравнение переменной с самой собой в тесте). `CS1591` (публичный член без `///`) роняет сборку только в `Finance.Domain` и `Finance.Application`: `GenerateDocumentationFile` в `Directory.Build.props` включён по имени проекта. В тестах и `Finance.App` то же правило действует, но компилятор его не проверит.
- `Finance.App` собирается только под `net10.0-android`. Папки `Platforms/iOS`, `MacCatalyst`, `Windows` удалены намеренно — приложение только для Android; шаблон MAUI создаёт их заново, восстанавливать не надо.
- В `Finance.App` короткое имя `Application` значит пространство имён `Finance.Application`, а не тип MAUI: вложенное пространство имён побеждает и `using`, и одноимённый псевдоним. Тип MAUI подключён псевдонимом `ControlsApplication` в `GlobalUsings.cs`. Пока прикладной проект был пуст, столкновения не было, и шаблон MAUI собирался.
- Найти, что делает MAUI внутри, можно по символам сборки: `strings` в Git Bash нет, зато `grep -ao "ИмяМетода[A-Za-z]*"` по `~/.nuget/packages/microsoft.maui.controls.core/<версия>/lib/net10.0-android36.0/Microsoft.Maui.Controls.dll` перечисляет имена методов — они лежат в сборке обычным текстом. Так выяснилось, что `UpdateStatusBarColor` в MAUI 10 нет и строку состояния красит контейнер шапки.

- **`dotnet build Finance.slnx` и `dotnet test` параллельно не запускаются:** они пишут в общие `obj`, и одна из команд падает с `CS2012` (файл занят `VBCSCompiler`). Фоном гоняется одна из них, а не обе.

- **`dotnet test` не собирает `Finance.App`** — только пять остальных проектов. Ошибку компиляции страницы поймает лишь `dotnet build Finance.slnx` (около 40 с против секунды на тестах). После переезда типа между пространствами имён нужны оба прогона: страницы MAUI видит только сборка решения.

- **`grep -rn` печатает имя файла перед строкой, а в этом репозитории каждый путь содержит `Finance`.** Отсев по содержимому (`| grep -v "Finance.Domain"`) выбрасывает заодно все строки любого файла из `src/Finance.Domain`, и поиск молча возвращает пустоту. Имя файла отрезается до отсева: `| sed 's/^[^:]*:[0-9]*://'`.
- **`grep -P` в этом Git Bash не работает вовсе** — «supports only unibyte and UTF-8 locales», и `LC_ALL=C` не помогает. Ретроспективная проверка (`(?<!Finance\.)`) недоступна и в инструменте Grep: ripgrep отвергает её разбором. Ищется без неё, лишнее отсеивается вторым проходом.
- **Редактор помечает `using Finance.Application.Texts` и каждое `UiTexts.*` ошибкой (CS0234, CS0103) — это ложная тревога.** Класс собирается из `.resx` в `obj` во время сборки, и редактор его не видит. Верить нужно `dotnet build`, а не подсветке.
- **`const` не принимает значение из ресурса** — `CS0133`: свойство сгенерированного класса вычисляется в рантайме. Константа, которой досталась строка интерфейса, переписывается в `private static string X => UiTexts.Key`.
- **`InvariantGlobalization` включать нельзя никогда.** На нём умирают `d MMMM`, `ru-RU` и разбор часовых поясов, а сборка об этом молчит. Запрет продублирован комментарием в `Directory.Build.props` рядом с `NeutralLanguage`.
- **Временно отключить код `if (false)` нельзя:** `CS0162` (недостижимый код) при `TreatWarningsAsErrors` роняет сборку. Когда сверку ломают нарочно, кусок закомментировывается `/* */` или правится сама строка.

Релизная сборка, миграции и публикация:

```
dotnet build -c Release                                      # проверять именно на релизной сборке
dotnet ef migrations add Имя -p src/Finance.Application -s src/Finance.Application -o Infrastructure/Storage/Migrations
dotnet publish src/Finance.App/Finance.App.csproj -f net10.0-android -c Release -p:AndroidPackageFormat=apk -o apk-builds/1.0.0+$(git rev-parse --short HEAD)
```

**Каждая публикация уходит в свою папку `apk-builds/<версия>+<хеш>/`.** Общая папка не годится: `publish` перед собой ничего не чистит, и остатки прошлого запуска лежат вперемешку со свежими — `.aab` пятичасовой давности рядом с сегодняшним `.apk` выглядит частью той же сборки. Хранятся три последние папки, остальные удаляются: каждая весит сорок мегабайт, а восстанавливается одной командой. Папка отсечена в `.gitignore` отдельной строкой — правило `artifacts/` её не ловит.

**Версия приложения растёт с каждой выкладкой на телефон.** `ApplicationDisplayVersion` — `1.0.x`, `ApplicationVersion` — это `versionCode` Android и считается из версии как `major*10000 + minor*100 + patch`; на меньший `versionCode` платформа обновление не ставит. Оба числа лежат в `Finance.App.csproj` для сборок с рабочей машины, а релиз получит их из тега `v1.0.x` и передаст в командной строке: заданное через `-p:` свойство у MSBuild глобальное и значение из проекта перекрывает. Расхождение числа в проекте с номером релиза — не ошибка, править его «для порядка» не нужно. Экран «О программе» показывает версию из манифеста, так что без роста номера все сборки на устройстве неотличимы.

Публикация кладёт рядом три файла. На телефон ставится только `ru.finance.tracker-Signed.apk`: соседний `ru.finance.tracker.apk` без подписи, Android отвергает его как повреждённый, а `.aab` — формат загрузки в Google Play, не пакет установки. Подпись отладочная, ключом из SDK; обновление поверх встанет только с той же подписью, так что переход на собственный ключ потребует удалить приложение вместе с базой — а с ней и всю историю, потому что обмена нет и база единственный источник правды. Отсюда порядок: свой ключ заводится до первого релиза и до переноса истории из чужого приложения, а не после.

В сгенерированной миграции `descending: new bool[0]` — это **все колонки `DESC`**, а не «ни одной»: пустой массив у EF значит «единообразно по убыванию». Частичный порядок пишется явным списком, как `new[] { false, true, true, true }` у индексов ленты счёта. Сверять стоит по SQL: `dotnet ef migrations script <ПредыдущаяМиграция>`.

Предкомпилированной модели EF нет и не будет, пока у таблиц стоит глобальный фильтр мягкого удаления: `dotnet ef dbcontext optimize` с ним падает, а фильтр важнее.
