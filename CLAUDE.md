# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Личный трекер финансов** — Android-приложение для персонального учёта финансов. Один пользователь, несколько его устройств.
Офлайн-first: источник правды — локальная база. Сервер только обменивает изменения между устройствами и **не содержит доменной логики**.

## Состояние репозитория

**Кода пока нет.** Репозиторий содержит только спецификацию ([docs/](docs/)), стартовые данные ([data/](data/)) и валидатор пресета ([tools/](tools/)). Решение, проекты и `docker-compose.yml` не созданы — Этап 0 из [PLAN.md](PLAN.md) не начат.

Практическое следствие: не предполагай существования файлов проектов. Перед ссылкой на класс, миграцию или страницу проверь, что они уже написаны. Из раздела «Команды» сейчас работает только валидатор пресета.

**Git не инициализирован** — истории нет, откатить правку нечем. Больнее всего это бьёт по [data/preset.json](data/preset.json): ключи категорий менять нельзя, поэтому ошибка в нём необратима. `git init` стоит сделать до Этапа 0.

## Стек

.NET 10 · MAUI (Android) · EF Core + SQLite на клиенте · ASP.NET Core Minimal API + PostgreSQL на сервере · xUnit

## Проекты

`Finance.Domain` (без зависимостей) · `Finance.Contracts` (DTO протокола, без зависимостей) · `Finance.App` (MAUI) · `Finance.Server` · `Finance.Domain.Tests`

**`Finance.Contracts` не ссылается на `Finance.Domain`.** Иначе сервер получит доменную логику транзитивно — ровно то, чего архитектура избегает. `Finance.Server` зависит только от `Contracts`.

## Правила, нарушение которых ломает данные молча

- **Идентификаторы — UUIDv7, генерирует клиент.** `ValueGeneratedNever()`. Никаких серверных автоинкрементов: записи создаются офлайн.
- **В SQLite идентификаторы хранятся TEXT** в каноническом виде. `Guid.ToByteArray()` без `bigEndian: true` переставляет байты. Ключ разрывает ничью в сортировке ленты (FR-LED-02), а монотонность UUIDv7 даёт локальность вставок в индекс — перестановка байтов ломает оба свойства.
- **Деньги — только `decimal`.** Сложение сумм в разных валютах обязано бросать исключение: общей суммы по валютам в этом приложении не существует.
- **Суммы всегда положительны, знак задаёт `kind`** (INV-01, INV-02). Расход, записанный отрицательной суммой, уедет в баланс дважды в одну сторону, и ошибка размажется по всей истории.
- **Моменты времени — UTC, `DateTimeOffset`, суффикс `_at_utc`. Календарные даты — `DateOnly`, суффикс `_on`, без конвертаций.** Дата операции в UTC уедет на сутки и сломает границы месяца.
- **«Сегодня» — локальная дата пользователя**, не `UtcNow.Date`.
- **Часовой пояс — идентификатор зоны, а не числовое смещение** (NFR-14). Смещение перестанет соответствовать зоне на переходе на летнее время.
- **Лента и баланс по счёту: `UNION ALL` двух запросов.** `WHERE account_key = ? OR counter_account_key = ?` не использует индексы. Сами индексы обязательны (NFR-04): составной по счёту, дате операции, `created_at_utc` и ключу и отдельный по счёту назначения — без них объединение выигрыша не даёт.
- **Удаление мягкое всегда.** Физический `DELETE` не даст второму устройству узнать об удалении, и запись воскреснет.
- **Перед миграцией схемы — снимок базы** через `VACUUM INTO`, при неудачной миграции откат на него (NFR-06). Хранится одна последняя копия.
- **Слой синхронизации не проверяет доменные инварианты.** Он применяет пришедшие строки как есть. Проверки — только при вводе (SYN-18, SYN-19).
- **Курсор синхронизации — счётчик изменений на сервере, а не метка времени** (SYN-02). Часы устройств расходятся, по времени изменения теряются.
- **Очередь отправки чистится только по списку ключей, принятых сервером** (SYN-08, SYN-09). Очистка «по факту отправки» теряет записи при обрыве посреди пачки.
- **Порядок применения изменений: счета → места → группы → подкатегории → операции** (SYN-10). Полученное сначала буферизуется и упорядочивается клиентом (SYN-11).
- **Пресет засевается с фиксированной меткой `updated_at_utc`** из [data/preset.json](data/preset.json) (`seededAtUtc`, заведомо давняя — SEED-03). Текущее время затрёт пользовательские переименования при установке на новое устройство.
- **Ключи категорий в [data/preset.json](data/preset.json) и `namespace` не меняются никогда** — из них выводятся UUIDv5. Значки берутся только из набора [data/icons.json](data/icons.json) (SEED-07).
- **Цвета — только именованные токены темы** (ResourceDictionary + AppThemeBinding). Прямой hex в разметке экрана сломает тёмную тему молча (NFR-24).
- **Удаление места не трогает строки операций.** Массовое обнуление ссылок породит сотни строк в очереди отправки и искусственные конфликты слияния (FR-PAY-05).

## Как устроен код

- **Конструкторы доменных типов закрыты.** Создание — фабричным методом с полной проверкой, восстановление из хранилища — отдельным путём без проверок. Один общий конструктор превратит чтение из базы в валидацию (§9.6). Путь восстановления публичный, и его комментарий обязан говорить, что проверок нет.
- **Пишущий путь идёт через доменные типы, читающий — напрямую в плоские модели** с проекцией на стороне базы. Доменные сущности между контекстами не передаются.
- **Обработчики вызываются моделями представления напрямую через интерфейсы.** Посредник для диспетчеризации не вводится.
- **`updated_at_utc`, наполнение очереди отправки и события изменения проставляются при сохранении**, в переопределении `SaveChanges`. Засев пресета идёт в обход этого механизма.
- **Межтабличные проверки** (дата операции против дат открытия обоих счетов) — доменным сервисом, а не внутри сущности.
- **Проверять на релизной сборке** (TECH-03): отсечение неиспользуемого кода ломает механизмы на отражении.

## Язык и комментарии

- **Код — только английский.** Имена типов, методов, полей, таблиц и колонок. Смешанные имена вида `AddОперация` недопустимы.
- **Имена берутся из [CONTEXT.md](CONTEXT.md).** Там у каждого понятия ровно одно русское и ровно одно английское имя, а рядом список того, чем его называть нельзя. Новый термин сначала попадает в словарь, потом в код.
- **Комментарии — на русском.** Публичные члены комментируются XML-документацией (`///`), внутри методов — обычными комментариями.
- **Все публичные методы и сущности покрыты комментариями.** Приватные — только там, где неочевидно почему.
- **Комментарий краткий и содержательный: зачем, а не что.** Пересказ сигнатуры хуже, чем ничего: он устаревает молча и его никто не перечитывает.
- **В доменной сущности комментарий описывает инвариант и контракт, а не прикладной сценарий. В слайсе `Features/*` — наоборот: сценарий, а не доменное правило.** Иначе одно правило окажется записано в двух местах и разойдётся при первой же правке.
- **Документация ([docs/](docs/), [PLAN.md](PLAN.md), этот файл) сейчас на русском.** Планируется перевод на английский; после перевода дополнения пишутся на английском.

## Команды

```
python tools/validate_preset.py          # сверка пресета с требованиями (Windows) — работает сейчас
python3 tools/validate_preset.py         # то же на Linux и macOS
```

На Windows команда называется `python`: `python3` там — заглушка Microsoft Store, завершается с ошибкой.
Для читаемого вывода кириллицы в консоли Windows: `PYTHONIOENCODING=utf-8 python tools/validate_preset.py`.

**Скрипт временный.** Он существует, потому что проекта ещё нет. На Этапе 0 те же четыре проверки переезжают в `Finance.Domain.Tests`, а [tools/validate_preset.py](tools/validate_preset.py) удаляется — держать две реализации одной проверки на двух языках нельзя, они разойдутся.

После создания решения (Этап 0 и далее):

```
dotnet build
dotnet test                              # инварианты домена
dotnet ef dbcontext optimize             # ПЕРЕЗАПУСКАТЬ после каждого изменения сущностей (TECH-02)
docker compose up -d                     # postgres для сервера
```

## Чего не делать

- Не добавлять доменную логику на сервер.
- Не вводить второй идентификатор рядом с `key`.
- Не расширять дерево категорий до трёх уровней — вместо этого поле «Место» (`place_key`).
- Не реализовывать то, что помечено в [docs/requirements.md](docs/requirements.md) как вне MVP: аналитику, теги, вложения, будущие и повторяющиеся операции, импорт, OAuth.
