# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Личный трекер финансов** — Android-приложение для персонального учёта финансов. Один пользователь, несколько его устройств.
Офлайн-first: источник правды — локальная база. Сервер только обменивает изменения между устройствами и **не содержит доменной логики**.

## Состояние репозитория

**Этапы 0–2 закрыты.** Домен готов и покрыт тестами. В `Finance.Application` есть хранилище (контекст, миграция `Initial`, резервная копия, инициализация стартового набора), общие запросы балансов, ленты, категорий, мест и состояния настроек и слайсы: `Features/Accounts` (карточка, справочник, порядок), `Features/Balances`, `Features/Transactions/Card` (запись, правка, удаление, набор суммы), `Features/Transactions/Pick` (выбор счёта, подкатегории и места отдельными экранами), `Features/Feed` (общая лента и лента счёта), `Features/Categories` (справочник, карточки группы и подкатегории, удаление с переездом операций), `Features/Places` (справочник со счётчиками, карточка, переименование и удаление), `Features/Settings` (тема, часовой пояс, «О программе»), `Features/More` (подписи-счётчики раздела «Ещё») и `Features/Report` (отчёт за месяц: группы, подкатегории, операции). В `Finance.App` — каркас из четырёх вкладок, страницы этих слайсов, контрол `Controls/Icon`, рисующий значки по ключу, `Controls/AmountKeypad` — клавиатура суммы, `Controls/FeedList` — общий список для обеих лент — и `Controls/IconGrid`, выбор значка категории. MVP собран целиком; что дальше — в чеклисте [PLAN.md](PLAN.md).

Практическое следствие: перед ссылкой на класс, миграцию или страницу проверь, что они уже написаны.

Правки в [data/preset.json](data/preset.json) необратимы даже с историей: ключи категорий менять нельзя, из них выводятся идентификаторы. Перед правкой стартового набора — `dotnet test`, после — снова: проверки живут в `Finance.Docs.Tests`.

## Границы MVP

Одно устройство одного пользователя, **без сети**. Обмен с сервером отложен целиком: сервер, протокол, очередь отправки, слияние правок — всё вне MVP. Поля схемы под обмен заведены сразу, чтобы не переделывать базу задним числом.

Отчёт о расходах и доходах по группам за месяц, наоборот, в MVP входит.

## Стек

C# 14 · .NET 10 · MAUI (Android 16+) · EF Core + SQLite · xUnit. Сервер на ASP.NET Core Minimal API и PostgreSQL — вместе с обменом, вне MVP.

## Проекты

`Finance.Domain` (без зависимостей) · `Finance.Application` (слайсы функций: команда, обработчик, запросы, модель представления; инфраструктура — папкой внутри) · `Finance.App` (MAUI: только страницы, навигация, ресурсы темы) · `Finance.Domain.Tests` (доменные правила) · `Finance.Application.Tests` (обработчики, запросы и модели представления на настоящей базе SQLite) · `Finance.Docs.Tests` (проверки стартового набора, покрытия доменных правил требованиями и тестами и согласованности документации)

Домен разложен по пяти папкам, и пространство имён совпадает с папкой: `Entities` (`Entity`, `Account`, `Category`, `Place`, `Transaction`), `Enums`, `Values` (`Money`, `Keys`), `Rules` (`Names`, `Dates`, `NameUniqueness`, `CategoryRules`, `TransactionRules`), `Errors` (`Invariant`, `DomainException`, `DomainMessage`). `Invariant` — перечисление, но лежит в `Errors`, а не в `Enums`: это каталог нарушений, который читается только вместе с `DomainException`.

Пространство имён `Finance.Domain.Tests` — потомок `Finance.Domain`, и доменные типы там разыменовывались объемлющим поиском, без единого `using`. После переезда типов в папки такой поиск их не находит: тесты перестают компилироваться там, где `using` никогда и не было. Трогая состав пространств имён домена, проверяй `dotnet build Finance.slnx`, а не только `dotnet test`.

Прикладной слой режется по функциям: `Features/Transactions/Add`, `Features/Balances`, `Features/Report`. Слайсы не ссылаются друг на друга; запрос, понадобившийся второму слайсу, переезжает в общую инфраструктуру.

**Обработчики и модели представления живут вне MAUI намеренно.** Обычная библиотека тестируется обычным xUnit, без эмулятора и без сборки под Android. В `Finance.App` остаётся только то, что без MAUI не существует.

`Finance.Contracts` и `Finance.Server` создаются, когда дойдёт до обмена. `Contracts` не будет ссылаться на `Domain`: сервер не исполняет доменную логику и не должен получать её транзитивно.

## Правила, нарушение которых ломает данные молча

Обоснование каждого — в [docs/adr/](docs/adr/), файлы названы по сути решения.

- **Идентификаторы — UUIDv7, генерирует клиент.** `ValueGeneratedNever()`. Никаких серверных автоинкрементов: записи создаются офлайн.
- **В SQLite идентификаторы хранятся TEXT** в каноническом виде. `Guid.ToByteArray()` без `bigEndian: true` переставляет байты. Ключ разрывает ничью в сортировке ленты, а монотонность UUIDv7 даёт локальность вставок в индекс — перестановка байтов ломает оба свойства.
- **В SQLite деньги лежат целыми копейками в `INTEGER`.** Провайдер кладёт `decimal` в TEXT, а по тексту не работают ни `SUM`, ни сравнение: баланс пришлось бы считать в памяти, подняв всю ленту. Перевод делает один конвертер, остальной код работает с `Money`.
- **Сумма — тип `Money`: `decimal` плюс валюта, не голый `decimal`.** Сложение сумм в разных валютах обязано бросать исключение: общей суммы по валютам в этом приложении не существует.
- **`Money.Create` считает записанные знаки, а не значение: `1.500` отвергается наравне с `1.505`.** Округление — решение формы ввода, хвост нулей после умножения срезает вызывающий код. Закреплено `[InlineData("1.500")]`; выглядит ошибкой и ею не является.
- **Суммы всегда положительны, знак задаёт `kind`.** Расход, записанный отрицательной суммой, уедет в баланс дважды в одну сторону, и ошибка размажется по всей истории; в отчёте он перевернёт долю в процентах.
- **Моменты времени — UTC, `DateTimeOffset`, суффикс `_at_utc`. Календарные даты — `DateOnly`, суффикс `_on`, без конвертаций.** Дата операции в UTC уедет на сутки и сломает границы месяца.
- **В SQLite момент времени лежит `TEXT` фиксированной длины с нулевым смещением** через один конвертер. Поставщик отказывается сортировать по `DateTimeOffset` (смещения могли бы различаться), а ленте нужна сортировка по `created_at_utc`; одинаковая длина и смещение делают порядок текста порядком времени.
- **«Сегодня» — локальная дата пользователя**, не `UtcNow.Date`.
- **Часовой пояс — идентификатор зоны, а не числовое смещение.** Смещение перестанет соответствовать зоне на переходе на летнее время.
- **Лента и баланс по счёту: `UNION ALL` двух запросов.** `WHERE source_account_key = ? OR target_account_key = ?` не использует индексы. Сами индексы обязательны: составной по счёту, дате операции, `created_at_utc` и ключу и отдельный по счёту зачисления — без них объединение выигрыша не даёт.
- **Общей ленте нужен свой индекс — по дате операции, `created_at_utc` и ключу, без счёта.** У двух индексов выше ведущая колонка — счёт, и сортировку по всем счетам они не обслуживают: главный список операций пошёл бы полным проходом с сортировкой во временном дереве. По составу колонок этого не видно, поэтому сверяется план запроса (`Общая_лента_сортируется_по_индексу`).
- **Удаление мягкое всегда.** В MVP обмена нет, но поля и правило заведены сразу: физический `DELETE` не даст будущему обмену узнать об удалении, и запись воскреснет. Переезжать на мягкое удаление после накопления данных дороже, чем завести его сразу.
- **Перед миграцией схемы — резервная копия базы** через `VACUUM INTO`, при неудачной миграции откат на неё. Хранится одна последняя копия.
- **Стартовый набор записывается с фиксированной меткой `updated_at_utc`** из [data/preset.json](data/preset.json) (`seededAtUtc`, заведомо давняя). Текущее время затрёт пользовательские переименования при переустановке.
- **Ключи категорий в [data/preset.json](data/preset.json) и `namespace` не меняются никогда** — из них выводятся UUIDv5. Значки категорий берутся только из набора [data/icons.json](data/icons.json); контуры к ним лежат в [data/icon-paths.json](data/icon-paths.json) (Tabler Icons, MIT), вшиваются в `Finance.App`, и у каждого ключа набора контур обязан быть — это сверяет `Finance.Docs.Tests`. Значки интерфейса (`check`, `sun`, `moon`, `world`, `info-circle`, `backspace`, `swap`, `credit-card`, `map-pin`, `chevron-right`, `chevron-down`, `lock`, `grip-vertical`, `plus`, `arrow-down-left`, `arrow-up-right`, `calendar`) лежат там же лишними ключами вне набора: в сетке выбора категории им делать нечего. Зеркального `chevron-left` в наборе нет и не нужен: `chevron-right` с `Rotation="180"`. Кнопка со значком — `Border` стиля `IconButton` с `TapGestureRecognizer`: `Button` значок-контур не вмещает.
- **Значок счёта выводится из типа и признака накоплений одним маппингом** `AccountIcon.For`. Он в общей инфраструктуре, а не в слайсе: тот же значок показывают балансы, справочник счетов и выбор счёта в форме, и разойдись они — один счёт выглядел бы на трёх экранах по-разному. Признак «скрыть из расчётов» сильнее типа: у накоплений свой значок, а не значок карты или наличных.
- **Цвета — только именованные токены темы** (ResourceDictionary + AppThemeBinding). Прямой hex в разметке экрана сломает тёмную тему молча. Контраст текста к фону не ниже WCAG AA — сверяется `ContrastTests` по таблице пар «текст на фоне»; новый токен текста добавляется и в неё, иначе бледная подпись пройдёт незамеченной. Меняя фон тёмной темы, прогоняй `ContrastTests` сразу: `AccentDark` на `SunkDark` стоит у порога 4,5, и осветление фона на две ступени его роняет. Палитра макетов (`[data-theme="dark"]` в `docs/ui/mockups.html`) правится вслед, затем пересборка прототипа.
- **Признак, который модель завела для экрана, обязан быть привязан в разметке.** `IsNegative` у балансов и `IsBusy` у списков были описаны в моделях и не использованы: требование считалось выполненным, а на экране его не было. Заводя признак, доводи его до разметки в той же правке.
- **Тему и версию приложения прикладной слой получает снаружи**, параметрами `AddFinance`: что такое тёмное оформление окна и где лежит манифест, знает только MAUI. Тема применяется при каждом запуске, включая системную, — платформа помнит выбор прошлого запуска, и без явного сброса возврат к системной теме не подействует.
- **Возврат настройки к системному значению — удаление строки**, а не запись слова «системный». Это касается часового пояса: записанное значение не переехало бы вместе с пользователем. Тема — исключение, там системная тема записывается: иначе её не отличить от первого запуска.
- **Удаление места не трогает строки операций.** Операции с удалённым местом показываются как операции без места; массовая правка ссылок запрещена.
- **Переводы не входят в отчёт** и не считаются ни расходом, ни доходом. В итог дня общей ленты перевод входит как расход счёта списания, только если счёт зачисления в итог не входит (валютный или скрытый из расчётов): деньги ушли из учитываемых сумм. Перевод между двумя учитываемыми счетами итог дня не меняет. Разница с отчётом намеренная.
- **Валютная операция в отчёт не входит вовсе, а в ленте видна.** Поэтому третий уровень отчёта читает свой запрос, а не `IFeedQuery`: общий запрос дал бы шапку экрана, не сходящуюся со строками под ней. Предикат «счета, входящие в суммы» — `CountedAccounts`, один на итог дня и на отчёт.

## Стиль C#

Порядок приоритетов: **корректность → читаемость → производительность**. Образец — [соглашения .NET](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions), [Framework Design Guidelines](https://learn.microsoft.com/dotnet/standard/design-guidelines/) и [правила анализатора производительности CA18xx](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/performance-warnings).

**Самая свежая версия языка, возможности — по максимуму.** `LangVersion` в `Directory.Build.props` стоит `latest`: с SDK .NET 10 это C# 14. Старый синтаксис при наличии нового — повод переписать.

- file-scoped namespace, `using` вне пространства имён, `using var` без фигурных скобок; один тип — один файл;
- collection expressions `[...]` для любой коллекции, включая пустую;
- pattern matching и `switch`-выражения вместо цепочек `if`/`is`/приведений; `is` с константой вместо `==` для перечислений;
- `required` и `init` вместо конструкторов-перечислителей; `field` в свойстве вместо ручного поля ради одной проверки;
- extension members (блоки `extension`), `?.=`, `nameof` открытых обобщений, raw string literals вместо экранирования;
- ключевые слова типов (`string`, `int`), `var` — только когда тип виден справа (`new`, литерал, приведение); в `foreach` тип пишется явно;
- тело-выражение `=>` для методов из одного действия; именованные аргументы там, где подряд идут `null`, `true` или `false`;
- `Func<>`/`Action<>` вместо своих делегатов; `&&`/`||`, а не `&`/`|` в условиях;
- проверки аргументов — встроенными `ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace` и подобными;
- ловить только то, что можно обработать: голый `catch (Exception)` без фильтра запрещён; повторный выброс — `throw;`.

**Первый член перечисления — `Unknown = 0`, номера у всех членов проставлены явно.** `Unknown` значит неинициализированную переменную и настоящим значением не бывает ни у одного перечисления; явные номера держат значение члена на месте, когда строки в файле переставляют. Перестановка без номеров молча меняет смысл всего, что успело номер запомнить. Исключение — `[Flags]`: там нулевой член называется `None` и значит «ничего не выбрано», второй нулевой рядом с ним неотличим от первого (`DataChange`). Проверять `Unknown` в домене отдельным правилом не нужно: новое доменное правило — это член `Invariant`, строка в требованиях, проверка и тест. `Invariant.Unknown` из сверки покрытия исключён явно — правилом он не является.

Хранению это ничем не грозит: перечисления лежат в SQLite именем, а не номером (`HaveConversion<string>()` в `FinanceDbContext`), и стартовый набор разбирается `JsonStringEnumConverter` тоже по имени. Ни миграции, ни правки [data/preset.json](data/preset.json) добавление `Unknown` не требует.

**Исключения ради доменных правил** — у доменных типов с фабричным методом всё, что создаёт или меняет значение в обход проверок, не используется. Первичный конструктор нельзя сделать закрытым. Открытый `init` и `required` позволяют собрать объект инициализатором мимо фабрики. `with` у `record` и `record struct` копирует без проверок. Значение доменного типа меняется только методом с проверкой; `required`/`init` — для плоских моделей чтения, команд и моделей представления. Типам без фабрики (исключениям, моделям чтения) первичный конструктор можно.

**Производительность — максимальная, пока не страдает понимание кода.** Бесплатное по читаемости делается всегда:

- классы `sealed` по умолчанию, наследование — осознанное решение; маленькие типы-значения — `readonly struct` (`readonly record struct` — только вне домена, см. выше);
- статичные справочники (значки, стартовый набор) — `FrozenDictionary`/`FrozenSet`; поиск символов — `SearchValues`; регулярные выражения — `[GeneratedRegex]`;
- разбор, сравнение и форматирование — через `Span<T>`/`ReadOnlySpan<char>` и `TryFormat`, без промежуточных строк; `string.Create` с культурой вместо склейки через `+`, `StringBuilder` для длинного текста;
- `static` лямбды, где нет захвата; без LINQ во внутренних циклах, где он аллоцирует на каждой итерации; `Count`/`Length` вместо `Count()`, `TryGetValue` вместо `ContainsKey` + индексатор;
- ввод-вывод — только `async` с `CancellationToken` до самого низа, без `.Result` и `.Wait()`; в `Finance.Domain` и `Finance.Application` — `ConfigureAwait(false)`, в `Finance.App` — нет: там продолжение должно вернуться в поток интерфейса. Исключение — модели представления: они живут в `Finance.Application`, но правят привязанные коллекции, и `ConfigureAwait(false)` уводит эту правку из потока интерфейса;
- EF Core: чтение — `AsNoTracking` и проекция `Select` в плоскую модель на стороне базы, никаких N+1 и материализации всей таблицы ради фильтра в памяти.

Оптимизация, которая ухудшает читаемость (`stackalloc`, `ArrayPool`, `Unsafe`, ручные циклы вместо понятного выражения), — **только по замеру** BenchmarkDotNet или профилировщика и с комментарием, какой выигрыш она дала. Без цифр побеждает понятный код.

## Как устроен код

- **Конструкторы доменных типов закрыты.** Создание — фабричным методом с полной проверкой, восстановление из хранилища — отдельным путём без проверок. Один общий конструктор превратит чтение из базы в валидацию. Путь восстановления публичный, и его комментарий обязан говорить, что проверок нет.
- **Пишущий путь идёт через доменные типы, читающий — напрямую в плоские модели** с проекцией на стороне базы. Доменные сущности между контекстами не передаются.
- **Обработчики вызываются моделями представления напрямую через интерфейсы.** Посредник для диспетчеризации не вводится.
- **Модель представления, перечитывающая экран по изменению данных, наследует `ScreenViewModel`** и задаёт `Watched` и `ReloadAsync`. Подписка живёт от появления экрана до его ухода (`IScreenModel.Activate`/`Deactivate`, их зовёт `DataPage`), а не от конструктора: оповещение одно на приложение, и подписка из конструктора копилась бы с каждым заходом на экран. Событие приходит уже в потоке интерфейса — доставку задаёт `MauiProgram` через `AddFinance(..., dispatchToInterface)`. Сбой перечитывания уходит событием `ReloadFailed`: пользователь ничего не нажимал и принял бы устаревшие числа за нынешние.
- **Обработчик события в `Finance.App` синхронный и зовёт `Guarded.Run`.** `Guarded` — единственное место проекта, где `async void` разрешён, и единственное, где он с перехватом: в остальных невыловленное исключение не всплывает к вызывающему, а роняет процесс, и окно закрывается молча. Тело обработчика уезжает в приватный `async Task`. Сверяется тестом `Обработчики_событий_не_объявлены_async_void` — компилятор на такой обработчик не жалуется ни единым предупреждением.
- **Операции одного счёта с обеих сторон читаются через `AccountTransactions.BothSides`** (`UNION ALL` двух выборок). Условие `source = ? OR target = ?` в запросе — ошибка, даже для разовой проверки; SQL ленты счёта сверяется тестом.
- **План запроса снимает общий `QueryPlan.ExplainAsync`.** Внутри — отрезание ведущих `.param set` (это команды оболочки, база на них падает с `near "."`) и чтение колонки через `GetString(reader.GetOrdinal("detail"))`: перегрузки `GetString(string)` у `SqliteDataReader` нет. Образцы — `Общая_лента_сортируется_по_индексу` и `Суммы_месяца_не_идут_полным_проходом`.
- **У сводного запроса план сверяется от обратного.** `GROUP BY` с `ORDER BY SUM(...)` всегда даёт `USE TEMP B-TREE`, а планировщик вправе пойти и от счетов, и от операций — оба плана хороши. Плохо ровно одно: `SCAN` по таблице операций; псевдоним таблицы для проверки вынимается из самого SQL, а не угадывается.
- **Набор суммы и вычисление — разные типы: `AmountInput` и `AmountExpression`.** Считать можно и то, что набрать нельзя: выражение приходит ещё и с внешней клавиатуры. Знаки действий на клавиатуре типографские (`−` U+2212, `×`, `÷`); клавиша с обычным дефисом молча не примется ни одним из них.
- **Цифры и действия на клавиатуре суммы — два блока рядом: сетка цифр 3×4 и столбец из пяти действий (`÷ × − + =`).** Между строками столбца разделителей нет: клавиши стоят вплотную и читаются как один блок, а от цифр его отделяет просвет цветом страницы. Высоту клавиш поэтому задают сетки блоков, а не стиль клавиши: рядов четыре и пять, и сойтись по общей высоте они обязаны сами.
- **Итог выражения показывает клавиша «=», а не набор сам собой.** Пока в поле есть знак действия, итога нет вовсе: `AmountInput.HasOperation` про это и спрашивает, а `Collapse` по «=» сворачивает выражение в число и возвращает его в то же поле теми же знаками, какими его набирают. Считать за пользователя раньше, чем он попросил, значит показывать не тот итог, который он набирает. Сохранение при незакрытом действии не запрещено — записывается тот же итог, что показала бы «=».
- **Сохранение формы операции — зелёная клавиша в `Shell.TitleView`, у правого края.** ~~Раньше она стояла последней на клавиатуре суммы~~ — отменено по отзыву. `ToolbarItem` не годится: он рисуется подписью системного вида, а фона у него нет. Заголовок в такой панели тоже свой: штатный `Shell.Title` вместе со своим содержимым не показывается. Удаление переехало на ту же панель подписью — иначе сохранение оказалось бы не у края, а левее «Удалить». Фон под содержимым панели — `Shell.BackgroundColor` из стиля `Shell` (токен `Card`), а не фон страницы (`Paper`): контраст подписей в панели сверяется по паре с `Card`.
- **Клавиатура суммы уходит с экрана целиком, пока набирают заметку** (`IsVisible` контрола по `AreKeysVisible`): системной буквенной клавиатуре нужно место. Прежняя оговорка — «спрятать контрол целиком нельзя, сохранение ушло бы с экрана» — снята вместе с переездом сохранения в панель. Если снятие фокуса с `Entry` не придёт (а оно зависит от системной клавиатуры), клавиатуру вернёт касание поля суммы.
- **`IsEnabled` сам кнопку не гасит.** MAUI ставит нативному виду признак доступности, а залитый своим цветом фон остаётся тем же: погашенная кнопка выглядит нажимаемой и обещает нажатие, которого не будет. Гасит её `VisualState` `Disabled` в стиле — прозрачностью, а не своим цветом: погашенная пара «текст на фоне» иначе попала бы в палитру и в `ContrastTests`.
- **Кнопки форм зовут `SaveAsync` напрямую, а не через команду, поэтому защита от повторного запуска — флаг `IsSaving` в модели.** Кнопка гаснет по `CanSave`; без флага второе нажатие до ухода экрана записывало бы операцию дважды. У формы операции `CanSave` учитывает и флаг, и набранную сумму.
- **Формы не перечитываются при каждом появлении экрана:** `DataPage.ReloadsOnAppearing` у них `false`. На Android появление приходит и при возврате из фона, и перечитывание стёрло бы набранное. Списки перечитываются всегда.
- **Чтение, которое может отстать, считает номер поколения** (`_generation` в ленте и трёх уровнях отчёта): отставший запрос не перекрывает свежий и не снимает занятость раньше времени. Быстрое листание месяцев без него показывало бы группы одного месяца под шапкой другого.
- **Закрытие счёта с деньгами подтверждается диалогом на странице**, а не запретом домена: `AccountViewModel.ClosingWarning` называет остаток, домен закрытию не мешает.
- **Гонку в тесте на настоящей SQLite не подстроить: запись завершается на месте, и второе действие приходит после первого.** Обработчик или запрос оборачивается заглушкой с `TaskCompletionSource`, которая держит первый вызов, пока тест не отпустит (`DelayingSave` в `TransactionKeypadTests`, `DelayingReport` в `ReportTests`).
- **После удачного сохранения `IsSaving` не снимается, а после неудачного снимается — `IsSaving = done` в `finally`.** В эмуляторе второе нажатие успевает прийти после завершения первого сохранения, но до ухода экрана; модель формы одноразовая, и флаг остаётся поднятым. Обратная полярность (`!done`) стоила формы, застрявшей с подписью «Сохраняю…»: имя счёта оказалось занято, правило показалось, а сохранить исправленное имя было уже нечем. Оба конца проверяются: занятое имя гасит флаг, удачная запись оставляет.
- **Откат из копии проверяется хуком `DatabaseBootstrapper.BeforeMigrate`:** база портится между снятием копии и миграцией. Порча до копии восстановилась бы транзакцией самой миграции, и тест не отличил бы одно от другого. `TestDatabase.CreateUnprepared()` даёт службы без единого обращения к базе — для сценариев первого запуска.
- **Сбой конвертера значений EF приходит как `DbUpdateException`**, сама причина — в `InnerException`. `Assert.ThrowsAsync<InvalidOperationException>` на `SaveChangesAsync` не сработает.
- **Сумму в тексте сверяют через `Money.Create(...).Display`**, а не строкой: неразрывный пробел набрать в тесте нельзя, `Assert.Contains("1 000,00", …)` падает всегда. `Display` и `DisplaySigned` — extension-члены из `Finance.Application.Infrastructure` (`MoneyFormat`), не домена: тесту нужен этот `using`. Валюты в перечислении — заглавными (`Currency.RUB`).
- **`TransactionFixture.AccountAsync(openedOn:)`** задаёт дату открытия раньше `2026-01-01`: операции прошлых лет (високосный февраль) иначе отвергнет `TransactionNotBeforeAccountOpened`.
- **Счёт списания не предлагается в «Куда»:** у перевода свой список `TargetAccounts`, а экран выбора счёта получает его ключ параметром `excluded`. Общий список сообщал бы о запрете уже после нажатия «Сохранить», а сам запрет остаётся за доменом.
- **Счёт, категорию и место форма операции выбирает на отдельных экранах** (`Features/Transactions/Pick`), а решение возвращается через общий `TransactionPicks`: экран кладёт выбор и уходит обычным `GoToAsync("..")`, форма забирает его в `OnAppearing` через `ApplyPicks` и очищает. Параметром маршрута назад не вернуть: имя нового места — кириллица, а параметр к тому же остался бы в свойстве страницы до следующего перехода и подставился бы ещё раз. Побочная выгода — выбор проверяется обычным тестом, без эмулятора.
- **Ярлыки на значке приложения описаны ресурсом, а вид операции едет в дополнении к намерению.** Три ярлыка отличаются только значением `kind` при одном действии `ru.finance.tracker.action.ADD_TRANSACTION`: разбирает его один обработчик, и четвёртый вид не потребует ни нового действия, ни правки манифеста. Форма открывается абсолютным маршрутом поверх балансов, поэтому «назад» с неё ведёт на главный экран. Открытая несохранённая форма при этом теряется без вопроса: пользователь только что явно попросил новую операцию, а `DataPage` перехватывает лишь кнопку «назад».
- **Имя активности в системе задано явно** (`Name = "ru.finance.tracker.MainActivity"`). Без него платформа собирает имя сама, дописывая хеш сборки, и `targetClass` в описании ярлыков сослаться не на что: ярлыки при этом молча не появляются. Подписи ярлыков — только строковыми ресурсами, литеральный текст система не принимает вовсе.
- **Намерение холодного старта приходит раньше каркаса навигации.** Активность создаётся до первой страницы, и `Shell.Current` в этот момент пуст. Запрошенный вид ждёт в `ShortcutLaunch` и забирается из `AppShell.OnNavigated` — после первой навигации, когда переходить уже есть куда.
- **Вкладка открывается своим корнем: при смене вкладки стек прежней сбрасывается** (`AppShell.OnNavigating` запоминает уходящую секцию, `OnNavigated` зовёт у неё `PopToRootAsync`). Иначе стек вкладки живёт неделями: ушедший с ленты счёта на «Операции», вернувшись на «Балансы», видел бы не балансы, а ту же ленту. На форме операции и экранах выбора панели вкладок нет (`Shell.TabBarIsVisible="False"`): она съедала 80 dp под клавиатурой, а касание вкладки уводило с формы без вопроса — `DataPage` перехватывает только кнопку «назад». У остальных форм (счёт, группа, место) панель остаётся, и там несохранённое при смене вкладки теряется без вопроса.
- **Разворот группы правит список поштучно, а не пересобирает целиком.** `Lines.Clear()` с последующим `Add` приходит в `CollectionView` как сброс, и тот перерисовывает себя разом — плавного появления строк не будет. `Toggle` поэтому ищет индекс шапки и делает `Insert`/`RemoveAt`; полная пересборка остаётся за сменой вида, поиском и перечитыванием. Шеврон доворачивает `Chevron.TurnAsync`: знак ищется в ячейке по `AutomationId="Chevron"`, `chevron-right`, повёрнутый на четверть, совпадает с `chevron-down`, и ключ подменяется на довёрнутом знаке — иначе он прыгал бы.
- **Сумма красится по виду операции, а не по знаку: расход `NegativeLabel`, доход и зачисление `PositiveLabel`, списание перевода — обычным текстом.** У перевода сумма тоже отрицательна, и красный на нём читался бы как ещё одна трата. Отсюда `IsExpense` рядом с `IsPositive` в `FeedRowItem`: одного знака суммы для цвета не хватает. В отчёте переводов нет, и там `IsExpense` выводится из вида строки. Итог экрана красится цветом, а не подменой стиля: у `TotalLabel` свой шрифт.
- **Список категорий — плоский, а не сгруппированный: это цена аккордеона.** `CollectionView` с группировкой прячет заголовок вместе с содержимым, а свёрнутой группе заголовок как раз и нужен. Шапка и строка различаются признаком (`IsGroup`), отступ второго уровня даёт распорка `BoxView` слева — `Padding` в модели завести нельзя, `Thickness` там был бы типом MAUI.
- **В справочнике категорий у строки группы две роли:** касание строки открывает карточку, касание шеврона разворачивает. Поэтому шеврон сидит в своей ячейке с собственным `TapGestureRecognizer` и отступом: знак шириной в два десятка точек пальцем не поймать. На экране выбора роль одна — там разворачивает вся шапка.
- **Поиск и переключатель вида пересобирают список из прочитанного**, а не ходят в базу: их дёргают на каждую букву. Проверено обёрткой-счётчиком `CountingCategories` в тестах.
- **Полоса доли в отчёте — штатный `ProgressBar`**: `Progress` долей единицы, `ProgressColor` токеном темы, высота 4. Конвертеров значений в проекте нет, и ради ширины полосы заводить их не понадобилось.
- **Карточка нарушенного правила стоит над клавиатурой, вне прокручиваемой части формы.** Внизу экрана она видна всегда, и подводить к ней прокруткой не нужно — прежний подвод по первому измерению карточки убран вместе с ней. Фон у карточки свой (`ErrorCard`): красный текст на белом читается как подпись, а не как ошибка.
- **Уход с несохранённой формы спрашивает подтверждение.** `IFormModel.IsDirty` считается сравнением текущих полей со снимком на момент загрузки — кортежем или `readonly record struct`. Список «что считать правкой» отдельно от полей заводить нельзя: он разойдётся с ними при первом же новом поле, и правку молча потеряют. Всё подставленное снаружи — счёт с ленты, вид с ярлыка — ставится до снимка: после него форма считалась бы правленой, и уход с той, к которой не притронулись, спрашивал бы о чужом выборе.
- **`sender` у `Tapped` приходит то распознавателем, то самим элементом** — разметка одна, а поведение платформы разное. Данные строки берутся общим `BindableObject { BindingContext: … }`, а до ячейки идут через `sender as Layout ?? (sender as GestureRecognizer)?.Parent as Layout` (`Chevron.Cell`). Проверка только на `GestureRecognizer` гасит касание целиком, и ни сборка, ни тесты об этом не скажут.
- **Пользователю показывается текст исключения только там, где он для него и писался** — у `DomainException` и `DatabaseMigrationException`. Остальное уходит общим сообщением и в журнал: текст из библиотеки ничего не говорит, а пугает.
- **Часовой пояс в тесте не пишется строкой:** `TimeZoneInfo.GetSystemTimeZones()` на рабочей машине отдаёт имена Windows, на устройстве — IANA. Зона для проверки берётся из самого списка; строкой задаётся только то, что ищется через `TryFindSystemTimeZoneById` — он понимает оба вида имён.
- **`Money.Display` разделяет разряды неразрывным пробелом.** Сверка с `"1 590,00"`, набранным обычным пробелом, не совпадёт никогда.
- **Лента читается через `IFeedQuery` постранично; итоги дней считает база отдельным сводным запросом по датам страницы**, а не суммированием строк на экране: день может не уместиться в страницу, а итог в его шапке обязан быть за весь день.
- **Шапка ленты счёта читает один счёт — `IAccountsQuery.ReadOneAsync`**, а не весь список с `FirstOrDefault`: полный список считает балансы всех счетов сводкой по всей истории операций, а одному счёту хватает двух выборок по его индексам (`AccountBalances.ReadMovementAsync`). Проекция строки счёта у обоих запросов одна, чтобы список и шапка не разошлись по полям.
- **Независимые чтения одного экрана запускаются разом и ждутся `Task.WhenAll`** (раздел «Ещё», два нижних уровня отчёта): у каждого запроса свой контекст из фабрики, и последовательные `await` складывали бы задержки. Результат забирается `await` уже завершённой задачи, не `.Result`. Через один `DbContext` так нельзя — он не потокобезопасен, и внутри обработчиков чтения остаются последовательными.
- **Дети категорий раскладываются по группам одним `ToLookup`**, а не `Where` по всему справочнику на каждую группу: пересборку списка дёргают на каждую букву поиска.
- **В query-синтаксисе LINQ слово `group` — ключевое**: переменная соединения или параметр лямбды с таким именем ломает разбор. Для группы категории используется `parent`, для результата `GroupBy` — `bucket`.
- **`updated_at_utc`, наполнение очереди отправки и события изменения проставляются при сохранении**, в переопределении `SaveChanges`. Инициализация базы идёт в обход этого механизма.
- **Межтабличные проверки: прочитанные данные подаются параметром, решение остаётся за доменом.** Где сущности хватает одного факта, правило живёт в ней (валюта счёта против «были ли операции»). Где нужны другие записи целиком — отдельный тип: `TransactionRules` (операция против счетов и категории), `CategoryRules` (приёмник группы), `NameUniqueness`. В хранилище домен не ходит никогда.
- **Проверять на релизной сборке**: отсечение неиспользуемого кода ломает механизмы на отражении.
- **Доменные правила названы, а не пронумерованы: перечисление `Invariant`.** `DomainException.Invariant` говорит, какое правило нарушено; тест сверяется с ним, а не с текстом. Имя члена читается само — `Invariant.ClosedAccountNotInNewTransaction`, — поэтому в коде, тестах и комментариях номера требований не пишутся.
- **Тест правила помечается `[Trait("Инвариант", nameof(Invariant.NameUnique))]`.** `Finance.Docs.Tests` сверяет три стороны: каждое правило из требований названо членом `Invariant` в строке таблицы, каждый член упомянут в требованиях ровно один раз и покрыт хотя бы одним тестом. Заготовки сущностей для тестов — `Given.cs`, имена тестов русские через подчёркивание. Правка операции моделируется снимком `Given.Snapshot` и `Replace` на той же записи: `previous` с чужим ключом отвергается.
- **Имя категории в тесте не повторяет имя из стартового набора:** `NameUnique` отвергнет заведение, и тест упадёт на подготовке данных, а не на проверке. «Еда», «Транспорт», «Дом» и прочие очевидные имена уже заняты.
- **Новое доменное правило — это четыре правки разом:** член `Invariant` с комментарием, строка в [docs/requirements/02-domain.md](docs/requirements/02-domain.md) с его именем в обратных кавычках, проверка в домене и тест с `[Trait]`. Пропуск любой роняет `dotnet test`.
- **Проверку, которая не может упасть, писать бессмысленно.** Новую сверку (стартового набора, покрытия, документации) сначала ломают нарочно — портят данные или убирают пометку, — убеждаются, что тест падает с внятным сообщением, и возвращают как было.
- **`DomainException.ThrowIf` — две перегрузки, обычная и ленивая.** Интерполированную строку компилятор отправляет в ленивую, обычную — в простую; сливать их нельзя, иначе текст сообщения будет собираться на каждую сумму и каждую дату. Это закреплено тестом `Текст_не_собирается_когда_требование_не_нарушено`.

## Язык и комментарии

- **Код — только английский.** Имена типов, методов, полей, таблиц и колонок. Смешанные имена вида `AddОперация` недопустимы.
- **Имена берутся из [CONTEXT.md](CONTEXT.md).** Там у каждого понятия ровно одно русское и ровно одно английское имя, а рядом список того, чем его называть нельзя. Новый термин сначала попадает в словарь, потом в код.
- **Комментарии — на русском.** Публичные члены комментируются XML-документацией (`///`), внутри методов — обычными комментариями.
- **Все публичные методы и сущности покрыты комментариями.** Приватные — только там, где неочевидно почему.
- **Комментарий краткий и содержательный: зачем, а не что.** Пересказ сигнатуры хуже, чем ничего: он устаревает молча и его никто не перечитывает.
- **`<summary>` и `<remarks>` пишутся построчно всегда, даже когда текст в одну строку.** Открывающая метка, текст, закрывающая метка — три строки. Однострочная запись `/// <summary>текст</summary>` не используется: дописать к ней второе предложение нельзя без переделки строки, и правка комментария выглядит в отличиях переписыванием, а не дополнением. `<param>`, `<returns>`, `<exception>` и `<typeparam>` остаются однострочными — это их обычный вид.

  ```csharp
  /// <summary>
  /// Рубль. Валюта итогов дня и отчёта — единственная, в которой считаются общие суммы.
  /// </summary>
  ```

- **Номера требований в код, тесты, этот файл и [PLAN.md](PLAN.md) не переносятся.** Разработчику шифр ничего не говорит: правило называется словами или членом `Invariant`. Номера — внутренняя разметка документов в [docs/](docs/), для их перекрёстных ссылок и проверок документации. Сверяется тестом `Номера_требований_не_попадают_в_код`; идентификаторы экранов (`A-01`, `D-09`) он не трогает — на макет ссылаться можно.
- **В доменной сущности комментарий описывает инвариант и контракт, а не прикладной сценарий. В слайсе `Features/*` — наоборот: сценарий, а не доменное правило.** Иначе одно правило окажется записано в двух местах и разойдётся при первой же правке.
- **Отменённое решение записывается, а не стирается.** Правка, сделанная и откаченная по отзыву, помечается в [PLAN.md](PLAN.md) зачёркнутым пунктом, а причина уходит в правило здесь: без этого следующая сессия предложит её заново как очевидное улучшение. Так помечен моноширинный шрифт сумм.
- **Документация ([docs/](docs/), [PLAN.md](PLAN.md), этот файл) сейчас на русском.** Планируется перевод на английский; после перевода дополнения пишутся на английском.

## Команды

```
dotnet test                                     # доменные правила, стартовый набор, покрытие правил тестами, документация
dotnet test --filter "Инвариант=NameUnique"     # тесты одного правила
python tools/build_prototype.py                 # пересобрать прототип из макетов — после КАЖДОЙ правки mockups.html
```

На Windows команда называется `python`: `python3` там — заглушка Microsoft Store, завершается с ошибкой. На Linux и macOS — `python3`.
Для читаемого вывода кириллицы в консоли Windows: `PYTHONIOENCODING=utf-8 python tools/build_prototype.py`.

Запись файла через heredoc (`cat > файл <<EOF`) запрещена: в Git Bash на Windows кириллица и кавычки ломают разбор, а кодировка зависит от кодовой страницы. Новый файл пишется целиком, существующий правится точечной заменой. Массовая правка нескольких мест сразу делается коротким скриптом на Python со `stdin` (`io.open(..., encoding='utf-8', newline='\n')`), без кириллицы в самом скрипте — **включая искомые строки**: кириллица в heredoc приходит в Python мозаикой (`'/// <summary>��������'`), `assert s.count(o)==1` падает с нулём, и правка выглядит как «шаблон не найден». Якорь берётся по ASCII-части строки; где ASCII-якоря нет — правится инструментом Edit, а не скриптом.

Скрипт, идущий по существующим файлам, читает и пишет их байтами: метка BOM определяется по первым трём байтам и возвращается на место, а конец строки берётся из самого файла (`'\r\n' if '\r\n' in text else '\n'`). В дереве файлы лежат с CRLF (`core.autocrlf=true`), и запись через `newline='\n'` переписывает их целиком: правка на две строки приходит в отличиях как файл, изменённый весь.

Скрипт правки длиннее пары десятков строк в heredoc не влезает: bash обрывает его с `syntax error near unexpected token 'newline'`. Такой скрипт пишется файлом в папку `artifacts/` (например, patch.py) инструментом Write и запускается через `python` с путём к файлу.

`git add` и `git commit` печатают по строке `LF will be replaced by CRLF` на каждый файл (`core.autocrlf=true`, `.gitattributes` нет): полсотни строк шума вместо результата. Из PowerShell хвост фильтруется `| Select-String -NotMatch "LF will be"`.

Многострочное сообщение коммита пишется **из PowerShell** here-string `@'…'@`, закрывающая метка — в нулевой колонке. Та же конструкция в Bash уедет в сообщение буквально: заголовком станет `@`, а правка задним числом потребует принудительной отправки.

**Ловушки сборки.**

- Решение — `Finance.slnx`, не `.sln`: `dotnet new sln` в .NET 10 создаёт новый формат, и `dotnet sln Finance.sln add` молча не находит файл.
- `dotnet build` принимает ровно один проект: два пути подряд дают `MSB1008`. Для нескольких — по решению целиком.
- `TreatWarningsAsErrors` включён. Чаще всего ломают `CS1573` (описан `<param>` не у всех параметров — описывай либо все, либо ни одного) и `CS1718` (сравнение переменной с самой собой в тесте). `CS1591` (публичный член без `///`) роняет сборку только в `Finance.Domain` и `Finance.Application`: `GenerateDocumentationFile` в `Directory.Build.props` включён по имени проекта. В тестах и `Finance.App` то же правило действует, но компилятор его не проверит.
- `Finance.App` собирается только под `net10.0-android`. Папки `Platforms/iOS`, `MacCatalyst`, `Windows` удалены намеренно — приложение только для Android; шаблон MAUI создаёт их заново, восстанавливать не надо.
- В `Finance.App` короткое имя `Application` значит пространство имён `Finance.Application`, а не тип MAUI: вложенное пространство имён побеждает и `using`, и одноимённый псевдоним. Тип MAUI подключён псевдонимом `ControlsApplication` в `GlobalUsings.cs`. Пока прикладной проект был пуст, столкновения не было, и шаблон MAUI собирался.
- Найти, что делает MAUI внутри, можно по символам сборки: `strings` в Git Bash нет, зато `python -c` с регулярным выражением по байтам `~/.nuget/packages/microsoft.maui.controls.core/<версия>/lib/net10.0-android36.0/Microsoft.Maui.Controls.dll` перечисляет имена методов. Так выяснилось, что `UpdateStatusBarColor` в MAUI 10 нет и строку состояния красит контейнер шапки.
- **`{Binding}` не видит `static`-свойство модели представления.** Привязка ищет член у экземпляра: `ItemsSource` молча остаётся пустым, список выбора открывается без строк, а сборка проходит без единого предупреждения. Подписи для `Picker` объявляются свойством экземпляра, данные держит закрытое статическое поле. Где значение и правда статическое (подпись клавиши разделителя), в разметке пишется `{x:Static controls:Тип.Свойство}` — расширение разметки, а не привязка.
- **Свой наследник `Shape` требует своей записи обработчика.** MAUI ищет обработчик по точному типу, а не по базовому: без `ConfigureMauiHandlers(... AddHandler<Icon, ShapeViewHandler>())` любой экран со значком падает при открытии с `HandlerNotFoundException`. Сборка при этом чистая.
- **Первый сегмент маршрута не смеет совпадать ни с `Route` вкладки, ни с другим зарегистрированным маршрутом.** Совпадение с вкладкой `Shell` принимает за переход на саму вкладку и бросает «Relative routing to shell elements is currently not supported». Совпадение с чужим маршрутом хуже: исключения нет, а `Shell` разбирает переход посегментно и кладёт в стек страницу каждого известного сегмента — `accounts/feed` с балансов открывал ленту счёта поверх справочника счетов, и «назад» уводило в справочник, которого пользователь не открывал. Отсюда плоские имена `account-feed`, `account-card`, `category-group`, `category-subcategory`, `place-card`; у `transactions/*`, `reports/*` и `settings/*` первый сегмент не зарегистрирован, и составное имя им не мешает.
- **В .NET 10 `ContentPage.SafeAreaEdges` по умолчанию `None`, и на Android 16 страница идёт под системные полосы.** Ставится не на страницу, а на корневой лэйаут: `Grid` и `StackLayout` по умолчанию `Container`, а `ScrollView` — `Default`, и ему область задаётся явно (`Container`; `SoftInput` он не понимает вовсе). Форме операции нужен `Container, Container, Container, All` снизу — иначе клавиша сохранения уезжает под жестовую полосу и под системную клавиатуру. Именно `All`, а не `SoftInput`: с одним `SoftInput` при открытой клавиатуре отступ снизу удваивался (клавиатура плюс панель), а после её ухода обнулялся, и «Сохранить» уезжала под трёхкнопочную панель навигации. Проверять с трёхкнопочной панелью: `adb shell cmd overlay enable com.android.internal.systemui.navbar.threebutton` (обратно — `disable`), с жестовой полосой ошибка почти не видна.
- **`BindableLayout` наполняет layout целиком и стирает статических соседей.** Кнопка или распорка, положенная рядом с `BindableLayout.ItemsSource` в тот же `StackLayout`, молча не рисуется: список заменяет всех детей своими. Соседи кладутся во внешний layout, а связанный список остаётся отдельным слоем — так устроены разделы валют на балансах и строка «Добавить счёт» под ними.
- **Анимации перешли на `*Async`:** `RotateToAsync`, `FadeToAsync` и прочие. Прежние `RotateTo`/`FadeTo` помечены устаревшими, и при `TreatWarningsAsErrors` сборка на них падает.
- **Пустое состояние соседом списка в той же ячейке `Grid` не работает.** Пустой `CollectionView` рисуется поверх и перехватывает касания: текст либо не виден, либо не прокручивается. Штатное место — `CollectionView.EmptyView` с обёрткой `ContentView`; видимость внутри неё вешается на `IsLoaded`, иначе состояние мигнёт до первого чтения.
- **`ItemSizingStrategy="MeasureFirstItem"` режет двухстрочные ячейки.** Высота фиксируется по первому измерению, и вторая строка (подпись под названием) обрезается наполовину. Списки проекта двухстрочные — стратегия остаётся `MeasureAllItems` по умолчанию. Свойство живёт на `CollectionView`, а не на `LinearItemsLayout`: в разметке слоя оно не компилируется.
- **Вид операции подписан своим цветом и своим знаком: три шаблона сегментов вместо общего.** Три одинаково серых слова читаются как подпись, а не как выбор, и расход от дохода глазом не отличить. Шаблонов три (`ExpenseSegmentTemplate`, `IncomeSegmentTemplate`, `TransferSegmentTemplate`), а не один с параметрами: цвет плашки живёт в сеттере `VisualState`, а тот принимает только готовое значение, не `TemplateBinding`. Переключатель «Расходы/Доходы» в отчёте тоже на этих шаблонах: общая плашка цветом действия под словом «Расходы» читалась цветом дохода. В справочнике и карточке группы остаётся общий `SegmentTemplate`: там выбирают раздел, а сумм рядом нет.
- **У `RadioButton` свой `ControlTemplate` — `SegmentTemplate`.** Встроенный шаблон MAUI рисует кружок на плашке со своим фоном мимо токенов темы: в тёмной теме она остаётся белой, и сборка об этом молчит. Переключатель вида — сегменты во всю ширину, как в макетах (`.seg`): доли `Grid` с `*`, а не `HorizontalStackLayout` по центру. В тёмной теме подпись выбранного сегмента — основным текстом, не акцентом: `AccentDark` на `AccentBackgroundDark` даёт контраст 3,9 при пороге 4,5. Пара, встречающаяся в одной теме, заводится в `ContrastTests` списком `single`, а не общим `pairs`.
- **`RefreshView.IsRefreshing` — двусторонняя привязка**, и модель обязана иметь у флага открытый сеттер: жест поднимает его сам. Один флаг на ожидание первого чтения и на обновление — второго заводить не нужно, спиннер жеста служит и индикатором загрузки.
- **Значок вкладки `Shell` — только `ImageSource`.** Контрол `Icon` (наследник `Shape`) туда не годится: SVG кладётся в `Resources/Images`, а ссылаются на него по `.png` — Resizetizer растеризует при сборке. Цвет даёт `Shell.TabBar*Color`, поэтому цвет в самом файле не важен. Знак на кнопке (`+`, `‹`, `›`) наоборот остаётся подписью: подпись перекрашивается вместе с темой, а растр пришлось бы держать в двух вариантах.
- **Суммы — своими стилями `AmountLabel`, `TotalLabel`, `AmountHero`, шрифт везде Open Sans.** Моноширинный для сумм пробовали и откатили по отзыву: выглядел чужим. Смысловой цвет суммы — `AmountPositiveLabel`/`AmountNegativeLabel`, а не подмена на `PositiveLabel`: триггер меняет стиль целиком и потерял бы кегль и шрифт суммы.
- **Строка состояния — цветом шапки по теме приложения, и это делает `MainActivity`, а не ресурсы.** В .NET 10 окно идёт от края до края: строка прозрачна, под ней контейнер шапки MAUI цветом `colorPrimary`. Стиль `MauiAppBarLayout` в `Platforms/Android/Resources/values/styles.xml` делает контейнер прозрачным (и без тени — иначе по бокам строки остаётся серая кромка), а подложку окна и вид значков красит `ApplyStatusBar` по `RequestedTheme`. `values-night` тут не помощник: тема, выбранная в настройках, ночной режим платформы не переключает. `colorPrimary` остаётся акцентом: им подписаны кнопки системного календаря, и белый спрятал бы «ОК». **Родитель этого стиля обязан быть из MaterialComponents:** с `ThemeOverlay.AppCompat.*` нижняя навигация `Shell` не находит нужных ей атрибутов оформления текста и падает при создании — «requires that you specify a valid TextAppearance attribute», — а приложение закрывается на старте, ещё до первой страницы. Сборка при этом чистая, и ни один тест этого не поймает.
- **Календарь в форме открывается через `DatePicker.IsOpen` (.NET 10)**, сам контрол на экране невидим (`Opacity="0"`, высота 1): дата показана строкой с чипами «Сегодня / Вчера / …», а `Focus()` диалог на Android не открывает.
- **Стрелка «назад» в шапке `Shell` мимо `OnBackButtonPressed` не идёт.** Перехватывать приходится обе кнопки порознь: аппаратную и жестовую — переопределением, стрелку — через `Shell.SetBackButtonBehavior` с командой.
- **`dotnet test` не собирает `Finance.App`** — только пять остальных проектов. Ошибку компиляции страницы поймает лишь `dotnet build Finance.slnx` (около 40 с против секунды на тестах).
- **В выводе `dotnet test` три строки итогов — по одной на `Domain`, `Application` и `Docs`.** Ошибка компиляции тестового проекта строку его итога не печатает вовсе, а остальные два проходят: `grep Пройден` покажет два «Пройден!» и промолчит про третий. Считай строки или лови ещё и `error`.
- **`grep -rn` печатает имя файла перед строкой, а в этом репозитории каждый путь содержит `Finance`.** Отсев по содержимому (`| grep -v "Finance.Domain"`) выбрасывает заодно все строки любого файла из `src/Finance.Domain`, и поиск молча возвращает пустоту. Имя файла отрезается до отсева: `| sed 's/^[^:]*:[0-9]*://'`.
- **`grep -P` в этом Git Bash не работает вовсе** — «supports only unibyte and UTF-8 locales», и `LC_ALL=C` не помогает. Ретроспективная проверка (`(?<!Finance\.)`) недоступна и в инструменте Grep: ripgrep отвергает её разбором. Ищется без неё, лишнее отсеивается вторым проходом.
- **Временно отключить код `if (false)` нельзя:** `CS0162` (недостижимый код) при `TreatWarningsAsErrors` роняет сборку. Когда сверку ломают нарочно, кусок закомментировывается `/* */` или правится сама строка.

**Проверки документации живут в `Finance.Docs.Tests` и идут обычным `dotnet test`.** Скриптов на Python для проверок больше нет: держать две реализации одной проверки на двух языках нельзя, они разойдутся. Сборщик прототипа остаётся — это инструмент документации, а не проверка. Свежесть сборки проверяется отпечатками источников, которые он проставляет в собранный файл: запускать Python из тестов нельзя, а прототип обязан соответствовать макетам.

HTML-документ вне макетов кладётся не в `docs/ui`, а рядом (так лежит `docs/design/`): проверки макетов ждут там ровно два файла и сверяют палитру и число экранов. Markdown же проверяется везде: ссылки, файлы в обратных кавычках, обозначения экранов и запрещённые слова из [CONTEXT.md](CONTEXT.md) — бытовой синоним накоплений из его списка «избегать» в отчёте об аудите уронил `VocabularyTests`.

Три ловушки этих проверок. Правка `docs/ui/mockups.html` или самого сборщика требует `python tools/build_prototype.py` следом — иначе отпечатки разойдутся и тест упадёт. Не упоминай удалённый файл в обратных кавычках: проверка считает это ссылкой на существующий путь. И новое функциональное требование обязано попасть в сценарий [docs/use-cases.md](docs/use-cases.md) — иначе требуется объяснение в [docs/uncovered.md](docs/uncovered.md), а это файл для требований, которым сценарий не нужен по существу, а не для тех, которым его не написали.

Снять макет картинкой (сверить с экраном приложения) можно только через локальный сервер: `python -m http.server 8777 --directory docs/ui` и `http://127.0.0.1:8777/mockups.html` — протокол `file:` в Playwright заблокирован. Тему в макетах переключает кнопка «Переключить тему».

Новый экран в макетах — это ещё и число экранов в шапке `docs/ui/mockups.html` и в списке документов этого файла: `DataNumberTests` сверяет каждое такое число с фактическим составом макетов, в том числе прописью.

Сверка, которой нужны исходники, а не документы, строится на `Documents.Files("*.cs")`: обход идёт от корня репозитория с отсевом `.git`, `bin`, `obj`, а `Documents.Lines` и `Documents.Relative` дают адрес строки для сообщения. Так сделаны `Номера_требований_не_попадают_в_код` и `Обработчики_событий_не_объявлены_async_void`.

Далее по ходу Этапа 1:

```
dotnet build -c Release                                      # проверять именно на релизной сборке
dotnet ef migrations add Имя -p src/Finance.Application -s src/Finance.Application -o Infrastructure/Storage/Migrations
dotnet publish src/Finance.App/Finance.App.csproj -f net10.0-android -c Release -p:AndroidPackageFormat=apk -o artifacts/apk
```

Публикация кладёт рядом три файла. На телефон ставится только `ru.finance.tracker-Signed.apk`: соседний `ru.finance.tracker.apk` без подписи, Android отвергает его как повреждённый, а `.aab` — формат загрузки в Google Play, не пакет установки. Подпись отладочная, ключом из SDK; обновление поверх встанет только с той же подписью, так что переход на собственный ключ потребует удалить приложение вместе с базой.

В сгенерированной миграции `descending: new bool[0]` — это **все колонки `DESC`**, а не «ни одной»: пустой массив у EF значит «единообразно по убыванию». Частичный порядок пишется явным списком, как `new[] { false, true, true, true }` у индексов ленты счёта. Сверять стоит по SQL: `dotnet ef migrations script <ПредыдущаяМиграция>`.

Предкомпилированной модели EF нет и не будет, пока у таблиц стоит глобальный фильтр мягкого удаления: `dotnet ef dbcontext optimize` с ним падает, а фильтр важнее (TECH-02).

## Проверка в эмуляторе

**Правка, которую видно в интерфейсе, проверяется в эмуляторе, а не одними тестами.** `dotnet test` не поднимает ни одной страницы: привязка к `static`-свойству, незарегистрированный обработчик контрола, маршрут поверх имени вкладки, кнопка, уехавшая с экрана вместе со скрытой панелью, — всё это собирается без единого предупреждения и обнаруживается только на устройстве. Тронул слайс `Features/*`, страницу или разметку — открой этот экран и пройди сценарий целиком: заведение, правку, удаление и нарушенное правило.

Развёртывание на запущенный эмулятор — той же командой после каждой правки:

```
dotnet build src/Finance.App/Finance.App.csproj -f net10.0-android -t:Run '-p:AdbTarget=-s emulator-5554'
```

Кавычки вокруг `-p:AdbTarget=...` обязательны: без них аргумент рвётся по пробелу, а MSBuild сообщает `XA0010` — «выбранное устройство не запущено», хотя оно работает.

Управление экраном:

```
adb exec-out screencap -p > artifacts/shot.png   # снимок; по нему же берутся координаты нажатий
adb shell input tap X Y                   # координаты в пикселях устройства
adb shell input swipe X1 Y1 X2 Y2 400     # прокрутка
adb shell input text "Karta%sosnovnaya"   # только ASCII, пробел — %s
adb shell input keyevent 4                # назад; 67 — стереть знак, 111 — скрыть клавиатуру
adb shell am force-stop ru.finance.tracker
```

Ярлыки на значке проверяются отдельно: снимок экрана приложения о них ничего не говорит.

```
adb shell dumpsys shortcut                              # состав ярлыков: идентификаторы, подписи, значки
adb shell am start -n ru.finance.tracker/.MainActivity -a ru.finance.tracker.action.ADD_TRANSACTION --es kind Income
adb shell input swipe X Y X Y 600                       # долгое нажатие на значке: меню ярлыков
```

- **После `-t:Run` приложение стартует ещё 5–6 секунд.** Нажатие, посланное раньше, уходит в заставку и теряется молча: снимок покажет главный экран, а сценарий не начался. Перед первым `input tap` — `sleep 6`.
- **Удержание дольше секунды меню не открывает:** лаунчер принимает его за перетаскивание значка и показывает режим правки рабочего стола. 600 мс открывают меню.
- **Холодный старт проверяется только после `am force-stop`:** иначе намерение уходит в живое приложение и проверяет совсем другую ветку кода.
- **Снимки кладутся в `artifacts/`** — папка в `.gitignore`. В корне репозитория они уедут в `git add -A` вместе с правкой.
- **Смена вида операции — уже правка формы.** Обратный ход после неё показывает «Уйти без сохранения?», и следующее нажатие уходит в диалог, а не на экран под ним. Прогоняя сценарий, снимай экран после каждого возврата.
- **Снимок — единственный способ узнать, что на экране.** Порядок всегда один: снял, посмотрел, нажал, снял снова. Координаты нажатий считаются по снимку, а не угадываются: разметка переезжает от состояния к состоянию. Снимок показывается уменьшенным, и рядом с ним написан множитель до пикселей устройства (на этом AVD 1080×2400 показываются как 900×2000, множитель 1,2) — `input tap` принимает пиксели устройства, поэтому координаты с картинки умножаются. Без пересчёта нажатие уходит выше цели и попадает в соседнюю строку.
- **Падение при старте с «valid TextAppearance attribute» бывает и при правильном `styles.xml`.** Ресурсы Android упаковываются послойно, и `obj`/`bin` проекта `Finance.App`, оставшиеся от состояния до правки стиля, переживают обычную пересборку: приложение падает так же, как падало тогда, а файл в дереве при этом верный. Лечится удалением `src/Finance.App/obj` и `src/Finance.App/bin` с полной пересборкой (около минуты). Прежде чем искать ошибку в разметке, проверь это.
- **Падение молчит.** Окно просто закрывается, и остаётся рабочий стол — ни сборка, ни экран ничего не скажут. Причина лежит только в журнале:

```
adb logcat -d | Select-String "FATAL EXCEPTION" -Context 0,3
```

Перед запуском — `adb logcat -c`: буфер переживает и переустановку, и перезапуск, а `-d` отдаёт его целиком. Без очистки снимок журнала показывает падение прошлой сборки, и исправленная выглядит сломанной. Метку времени в найденной строке всё равно стоит сверить с часами на снимке экрана.

- Культура берётся при старте процесса. После смены языка устройства нужен `am force-stop`: без него даты остаются в прежнем формате, а `Money.Display` — с прежним разделителем.
- Кириллицу `input text` не передаёт. Названия для проверки набираются латиницей — доменных правил это не касается.
- Двойное нажатие: два `input tap` подряд в одной команде (`adb shell input tap X Y; adb shell input tap X Y`). Между ними около 100 мс — хватает, чтобы первое сохранение завершилось, поэтому защита обязана переживать успех, а не только ожидание.

## Чего не делать

- Не начинать обмен с сервером: поля схемы заведены, кода быть не должно.
- Не вводить второй идентификатор рядом с `key`.
- Не расширять дерево категорий до трёх уровней — вместо этого поле «Место» (`place_key`).
- Не переиспользовать в документах номера аннулированных и отложенных требований: они помечены зачёркнутым заголовком и повторно не используются.
- Не реализовывать то, что помечено в [docs/requirements/01-scope.md](docs/requirements/01-scope.md) как вне MVP: теги, вложения, будущие и повторяющиеся операции, бюджеты, импорт, поиск и фильтры, экспорт.
