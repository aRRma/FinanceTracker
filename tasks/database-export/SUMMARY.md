# Решение и почему

Статус и вопросы — в [README.md](README.md), шаги — в [PLAN.md](PLAN.md).

## Решение коротко

Выгрузка — **сам файл базы SQLite**, снятый `VACUUM INTO`. Восстановление — **проверка и
миграция присланного файла во временной папке, затем перенос данных в рабочую базу встроенным
копированием SQLite (`SqliteConnection.BackupDatabase`) и перезапуск процесса.** Рабочая база
не трогается, пока присланный файл не прошёл все проверки и не доведён до текущей схемы.

## Варианты

| Вариант | За | Против | Итог |
|---|---|---|---|
| Файл SQLite через `VACUUM INTO` | Переносится всё как есть: идентификаторы, метки, мягко удалённые строки (надгробия нужны будущему обмену), настройки, версия стартового набора. Код снятия копии уже есть (`DatabaseBootstrapper.BackupAsync`). Старая выгрузка доводится теми же миграциями | Файл двоичный, глазами не читается | **выбран** |
| JSON с сущностями | Читается человеком | Второе описание схемы — правится при каждой миграции, забытое поле теряется молча. Запись тысяч строк обратно. Работы в разы больше | отклонён |
| Автокопирование Android (`allowBackup`) | Ничего не делать | Сроки и состав решает Google; файл базы может уйти без журнала, то есть нерабочим; финансы в облаке без явного согласия | отклонён, остаётся выключенным |

## Что пересмотрено при перепроверке по коду

Первая версия анализа (тот же день) предлагала метку `PRAGMA application_id`, отложенную
подмену файла при запуске (`finance.db.restore` + правка `DatabaseBootstrapper`) и копию текущей
базы для отмены восстановления. Всё это убрано:

- ~~Метка `application_id`~~ — свою базу отличает история миграций EF: первая миграция наша.
  Метку пришлось бы ставить отдельной правкой, а в установленных базах её нет.
- ~~Подмена файла при следующем запуске~~ — `BackupDatabase` переносит данные в рабочую базу
  одной транзакцией прямо на ходу: при сбое база остаётся прежней. Не нужны ни закрытие пула, ни
  удаление `-wal`/`-shm`, ни новый код запуска.
- ~~Миграция выгрузки после подмены~~ — **это была дыра, а не упрощение:** старая выгрузка
  мигрировала бы уже на месте рабочей базы, и при неудаче откат вернул бы ту же выгрузку, а
  приложение отказалось бы запускаться — текущие данные уже стёрты. Теперь миграция идёт на
  временном файле, до записи.
- ~~Копия текущей базы для отмены~~ — без кнопки «вернуть» пользователю она ничего не даёт.
  Вместо неё подтверждение показывает обе стороны: «Сейчас: N операций, последняя — дата. В
  файле: M операций, последняя — дата».
- ~~«Сохранить в…» как основной способ~~ — заменено рекомендацией «Поделиться», решение за
  пользователем (вопрос 1 в README).

## Факты кода, на которые опирается решение

- **`DatabaseBootstrapper`** (`Infrastructure/Storage`) уже умеет `VACUUM INTO` во временный
  файл с подменой готовым, миграции и откат. Зависит от `IDbContextFactory<FinanceDbContext>` и
  `DatabaseLocation`. Для временного файла он избыточен: копия перед миграцией и откат
  одноразовому файлу не нужны, а его сообщения обращены к обновлению приложения («верните предыдущую версию») — к присланному файлу они не подходят. Временный
  файл доводится прямо `Database.MigrateAsync` контекста над ним (`UseSqlite(путь)`;
  конструктору контекста нужен ещё `IClock`).
- **Пул соединений Microsoft.Data.Sqlite** включён по умолчанию и держит файл открытым после
  `Dispose` соединения: временный файл открывается с `Pooling=False`, иначе он не удалится.
- **`DatabaseLocation`** — путь базы, `BackupPath = Path + ".backup"` — одна копия перед
  миграцией. Выгрузку в этот слот класть нельзя: её затрёт следующая миграция.
- **Настройки живут в базе** (`SettingName`): `preset.version`, `time_zone.id`, `theme`,
  `transactions.last_account_key`. Переезжают с выгрузкой — это верно; стартовый набор повторно
  не применится, потому что версия набора приезжает вместе с ним.
- **`FinanceStartup`** готовит приложение один раз за запуск и запоминает удавшуюся подготовку;
  пояс ставится в `SystemClock`, тема — `ThemeApplier`. После восстановления это устаревает.
- **Экраны** (`DataPage`) перечитываются при появлении, но карточки и формы — нет
  (`ReloadsOnAppearing => false` у `AccountPage`, `GroupPage`, `PlacePage`, `SubcategoryPage`,
  `TransactionPage`), а стеки вкладок `Shell` живут свои. Открытая в другой вкладке карточка
  сохранила бы правку в объект, которого в восстановленной базе нет. Отсюда перезапуск.
- **`Application.Quit()` перезапуском не является:** на Android процесс и синглтоны DI живут
  дальше. Нужен новый запуск с очисткой задачи и завершение процесса — код в
  `Platforms/Android`.
- **EF не отвергает базу из будущей версии:** `Migrate` накатывает известные ему миграции и
  молча пропускает лишние строки истории. Проверка «нет незнакомых миграций» — своя.
- **Выбор файла** уже есть: `FilePicker.Default.PickAsync()` без отбора по типу на
  `AboutPage` (мессенджеры портят тип). Поток из него — не путь; SQLite нужен файл, поэтому
  сначала копия во временную папку.
- **`AndroidManifest.xml`:** `allowBackup="false"` — требование надёжности, не трогать.

## Что учесть

- **Шифрования нет.** В файле вся история; лежит там, куда его отдал пользователь. Пароль —
  отдельное решение, позже и только по просьбе.
- **Обмен в будущем.** Восстановив одну выгрузку на двух телефонах, получим два устройства с
  одним состоянием. Сейчас ни идентификатора устройства, ни очереди отправки нет — не мешает.
  В ADR записать: с появлением обмена состояние, привязанное к устройству, при восстановлении
  сбрасывается.
- **Размер страниц.** `BackupDatabase` в базу в режиме WAL требует одинакового размера
  страницы. У нас обе базы созданы одним приложением со значением по умолчанию; при
  расхождении SQLite вернёт ошибку, а не испортит данные — её показать общим сообщением.
- **Чужой и битый файл.** Не-SQLite падает на первом запросе (`SqliteException`, «file is not
  a database») — это ответ «файл не подходит», а не сбой.
- **Временные файлы.** Выгрузка и принятый файл кладутся в кэш приложения и удаляются при
  следующей выгрузке или после восстановления.
- **Требования сейчас прямо против.** `01-scope.md` — «экспорт» вне MVP, и тот же запрет
  повторён в «Чего не делать» `CLAUDE.md`; `SYS-08` — копии вне устройства нет; ADR-0007 и
  `use-cases.md` («Рассмотрено и отложено», «Сценария восстановления
  нет») ссылаются на это. Всё правится в шаге 1 плана, отменённое — зачёркнутым с причиной.
