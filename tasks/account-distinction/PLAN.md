# План реализации: цвет и значок счёта

Дизайн согласован — [SUMMARY.md](SUMMARY.md), полный документ варианта — [variant-5.html](variant-5.html).
План составлен 4 октября 2026 по коду ветки `master` (коммит `60a2e25`); имена файлов сверены.
Перед каждым этапом — свой навык из `CLAUDE.md`: `build`, `tests`, `maui`, `texts`, `emulator`.

## Что делаем

Счёт получает **цвет** из палитры «Предельная насыщенность» (восемь цветов) и необязательный
**значок по назначению** из набора в восемнадцать знаков. Знак счёта — скруглённый квадрат,
залитый цветом, значок на нём белый или тёмный. Он заменяет нынешний значок типа везде, где
виден счёт, и появляется жетоном перед названием счёта в строке общей ленты. Новый счёт
получает цвет сам — первый свободный по очереди; существующие получают цвета миграцией.
Выбор цвета и значка — отдельный экран, открываемый из карточки счёта.

## Решить до начала

1. **Цвета существующим счетам.** Рекомендация — раздать миграцией по очереди, в порядке
   `is_closed`, `sort_order`: открытые счета получают первые цвета, после обновления балансы
   уже разноцветные. Альтернатива — всем один цвет, пользователь раскрашивает сам. Вопрос задан
   пользователю 4 октября 2026, ответа нет; план написан под рекомендацию.

  `AccountBadge` (контрол) и режимы `Tile`/`Token`/`Header`.
- `docs/requirements/03-functional.md`, раздел «Счета»: новая строка — цвет и значок счёта,

### 2. Домен

- `src/Finance.Domain/Enums/AccountColor.cs`: `Unknown = 0`, далее явные номера `Blue = 1`,
  `Orange = 2`, `Sky = 3`, `Green = 4`, `Violet = 5`, `Magenta = 6`, `Red = 7`, `Pink = 8`.
  Номер — не очередь: очередь задаёт прикладной слой отдельным списком.
- `src/Finance.Domain/Entities/Account.cs`: свойства `Color` и `Icon` (`string?`); параметры
  в `Create` и `Restore` (комментарий `Restore` говорит, что проверок нет); методы `ChangeColor`
  и `ChangeIcon`. `Icon` нормализуется как `Category.Icon`: пустое и пробелы — `null`, иначе
  `Trim()`. Доменных правил нет: одинаковые цвета и значки разрешены, допустимость ключа —
  забота прикладного слоя.
- Тесты домена: нормализация значка, смена цвета, `Restore` без проверок.

### 3. Хранение и миграция

- `src/Finance.Application/Infrastructure/Storage/AccountConfiguration.cs`: колонка `color`
  (TEXT NOT NULL, `HaveConversion<string>()` — перечисление хранится именем) и `icon`
  (TEXT NULL).
- Миграция `AddAccountColorAndIcon` (навык `build`, раздел про `dotnet ef`): добавить колонки
  и раздать цвета существующим счетам по очереди — `ORDER BY is_closed, sort_order`, по кругу
  из восьми; удалённые мягко — тоже, им цвет не мешает. Резервная копия перед миграцией и
  восстановление старой выгрузки уже проходят через общий путь миграций.
- Тест по образцу `UnsortedGroupsMigrationTests`: база старой схемы с несколькими счетами,
  включая заблокированный, — после миграции цвета по очереди, значки пустые.

### 4. Прикладной слой

- **Очередь цветов** — `Infrastructure/AccountColors.cs`: список очереди (синий, оранжевый,
  голубой, зелёный, фиолетовый, пурпурный, красный, розовый) и `Next(IEnumerable<AccountColor>
  taken)` — первый не занятый, иначе по кругу. Зовут заведение счёта и (той же логикой в SQL)
  миграция. Тесты: пустой список, занятые, все заняты, заблокированный не занимает.
- **Набор значков счёта** — новый файл data/account-icons.json (восемнадцать ключей) и класс по образцу
  `IconCatalog`, вшитый ресурсом в `Finance.Application.csproj`. Проверку «у каждого ключа
  набора есть контур в `data/icon-paths.json`» распространить на новый файл.
- **Маппинг** — `Infrastructure/AccountIcon.cs`: `For(type, excludedFromTotals, chosen)` —
  выбранный ключ из набора, иначе прежнее правило по типу. Четыре вызова (`AccountRowItem`,
  `AccountTile`, `TransactionFormQuery`, `AccountPickerViewModel`) передают ключ и отдают ещё
  и цвет; пятый — новая плашка в шапке ленты счёта.
- **Чтение:** `Infrastructure/Queries/AccountsQuery.cs` и `AccountListItem.cs` — цвет и значок;
  `FeedQuery.cs` и `FeedItem.cs` — цвет и значок счёта и, у перевода, второго счёта (проекция
  на стороне базы, без N+1; планы запросов ленты сверяются тестами — навык `tests`).
- **Строка ленты** — `Features/Feed/FeedRowItem.cs`: `Caption` делится на префикс и счёт (имя,
  цвет, значок), у перевода — два счёта; общая лента показывает жетон, лента счёта — нет.
- **Карточка счёта** — `Features/Accounts/Card`: `SaveAccountCommand` и `SaveAccountHandler`
  принимают цвет и значок; новый счёт без явного цвета получает `AccountColors.Next` от цветов
  незаблокированных счетов. `AccountViewModel`: `Color`, `Icon` (`null` — по типу, значок
  следует за типом), снимок `IsDirty` включает оба поля, команда открыть экран выбора, приём
  выбора при появлении. `AccountCardQuery` и `AccountCard` — оба поля.
- **Экран «Цвет и значок»** — новый слайс `Features/Accounts/Badge`: модель с восемью цветами,
  сеткой значков, подсказками по названию (таблица из SUMMARY.md, раздел «Значки счёта») и
  предпросмотром. Выбор возвращается общим объектом по образцу `TransactionPicks`: экран кладёт,
  карточка забирает в `OnAppearing` и очищает.
- Тесты: `AccountCardTests` (новый счёт получает цвет, правка, `IsDirty`), `AccountCatalogTests`,
  `BalancesTests`, `FeedRowTests`, `FeedTests` (подпись и жетоны, перевод), новый файл для
  экрана выбора и подсказок.

## Риски

- **Подпись строки ленты из частей.** Ячейки `CollectionView` переиспользуются: жетон и подпись
  обновляются на каждую смену `BindingContext`. Проверять прокруткой длинной ленты и на
  крупном шрифте — сборка и тесты этого не видят.
- **Цвет из ресурсов по имени.** При смене темы контрол перечитывает цвет сам; без этого
  тёмная тема останется со светлыми заливками.
- **Миграция и восстановление.** Старая выгрузка проходит ту же миграцию — тест на базе
  старой схемы обязателен.
- **`IsDirty` карточки.** Цвет и значок, подставленные новому счёту, ставятся до снимка — иначе
  нетронутая форма спросит о несохранённом.
