# План: виды тестов и инструменты

Основание — [SUMMARY.md](SUMMARY.md). Отметки о готовности ставятся только здесь, в [README.md](README.md) — этап целиком.

Общее для всех этапов: новая проверка ломается нарочно в момент написания и падает с внятным сообщением; в конце этапа — полный `dotnet test` и сверка числа тестов с прошлым прогоном.

## 1. Пробелы домена, найденные Stryker

- [x] `Account.ChangeOpenedOn`: новая дата открытия ровно в день самой ранней операции принимается — граница `>` против `>=`.
- [x] `Dates.EnsureInRange`: дата ровно на нижней границе принимается, на день раньше — нет.
- [x] `Money`: `<` и `>` на равных суммах ложны, `!=` различает суммы и валюты.
- [x] `CategoryRules.ReceiverFor`: защищённая подкатегория отвергается самим `ReceiverFor`, а не только `Category.Delete`.
- [x] `CategoryRules.EnsureCanMove`: не группа и подкатегория из чужой группы — `ArgumentException`.
- [x] Текст ошибки: категория в переводе против пропущенной категории (`Transaction`), перенос в группу дохода против расхода (`CategoryRules`). Сверять с ресурсом, а не литералом.

Готово, когда повторный Stryker по домену не показывает этих выживших.

**Итог 6 октября 2026.** 13 новых доменных тестов (142 → 155), две проверки текста в старых тестах. Повторный прогон нашёл ещё четыре пробела, их добили тем же заходом:
- повтор прежней даты открытия при операции раньше неё — не сдвиг вперёд;
- `ReceiverFor` с подкатегорией чужой группы и `EnsureHasReceiver` с подкатегорией вместо группы при пустом списке — `ArgumentException`;
- текст занятого имени подкатегории называет её группу.

Stryker по домену: 97,2 % (было 80,2 %), выживших 5 и один непокрытый. Все без пользы:
- ветка отложенной сборки `DomainMessage` — скорость, а не поведение;
- `RuleTexts.Of` с подстановкой при пустом уточнении — у подписей без `{0}` текст тот же;
- удаление `EnsureIsGroup` для текущей группы в `EnsureCanMove` — следом идёт проверка принадлежности, а подкатегория принадлежит только группе, и ошибку ловит она.

## 2. Сверка с простой моделью на случайных данных

Главный вид тестов, которого нет. Генератор заводит сотни операций через `TransactionFixture`:
- счета разных валют, скрытые и заблокированные;
- переводы, возвраты в универсальных группах;
- даты на границах месяцев.

Наивный подсчёт в памяти отвечает на те же вопросы, что запросы.

- [x] Пробный тест с CsCheck: подключение, время, вывод зерна на сбое. Новая зависимость — с согласия пользователя; помехи — пробовать FsCheck.
- [x] Баланс счёта: начальный остаток плюс доходы минус расходы, переводы по сторонам.
- [x] Лента: страницы от курсора складываются в полный список без потерь и повторов; итог дня равен сумме строк дня по правилам итога дня.
- [x] Отчёт: группы сходятся с подкатегориями, переводы не входят, возврат вычитается из своей группы, набор счетов отчёта соблюдён.
- [x] Чистые функции:
  - сумма в копейки и обратно;
  - набор суммы через `AmountExpression`;
  - месяц отчёта строкой и обратно;
  - порядок ключей UUIDv7.
- [x] Число итераций подобрано так, чтобы полный `dotnet test` оставался в секундах; приём описан в навыке `tests`.

**Итог 6 октября 2026.** CsCheck 4.9.1 в прикладных тестах, согласие пользователя получено. Ошибок в коде сверка не нашла.

- **`ModelCheckTests`** — баланс (список и один счёт), лента (общая и счёта, страницы случайного размера, суммы строк, итоги дней), отчёт (три уровня, порядок групп, валюта, признак «посчитано не всё»). По 30 историй на тест, зерно у каждого прогона новое: до пяти счетов в рублях и долларах, скрытые и заблокированные, до 120 операций с переводами между валютами, возвратами, удалёнными строками, совпадающими моментами записи и датами на границах месяцев.
- **`PropertyTests`** — копейки туда и обратно, отказ от доли копейки, набор числа с любым разделителем, выражение слева направо, месяц отчёта строкой, порядок ключей по времени и совпадение порядка `Guid` в памяти с текстом в базе. По 10 000 входов.
- **Отступление от плана:** история пишется доменной фабрикой одной пачкой, а не через `TransactionFixture` и обработчик — так сотня операций на итерацию обходится в доли секунды. Межтабличные правила обработчика соблюдает сам генератор.
- **Нарочные поломки** — каждая поймана с зерном в сообщении: модель баланса, итога дня и отчёта; в коде — условие курсора ленты, учёт перевода в итоге дня, округление выражения, формат месяца. Не поймана одна, и это предел метода: служебная категория, единственная вне набора счетов, выпадает слишком редко. Для таких сочетаний остаются тесты на примерах.
- **Время:** прикладные тесты — 6 с вместо 4 при 30 историях, 7 с при 50; взято 30. Повтор сбоя — `dotnet test -e CsCheck_Seed=…`. Переменная `CsCheck_Iter` число итераций, заданное в коде, не перекрывает.

## 3. Stryker как инструмент проекта

- [x] Stryker в манифест локальных инструментов .NET и файл настроек с обоими тестовыми проектами. Строки `DomainFaults` и `ThrowIfNull` исключены из мутаций, чтобы выжившие были только по делу. Манифест — `dotnet-tools.json` в корне, настройки домена — `src/Finance.Domain/stryker-config.json`, выжившие списком — `tools/stryker_survivors.cs`.
- [x] Файл настроек для `Finance.Application` — `src/Finance.Application/stryker-config.json`. Кроме миграций и `Faults` исключены настройки EF (`*Configuration.cs`): модель строится раз на процесс и кэшируется, мутант в ней не вступает в силу, и выживает даже снятый `ToTable`. Исключён и `TimeZoneCities` — таблица данных.
- [x] Первый прогон по `Finance.Application`: замер времени и оценки, разбор выживших тем же порядком, что в этапе 1.
- [x] Команда и чтение отчёта — в навык `tests`. Запуск — перед релизом и после крупной правки правил; не на каждую правку и не в CI: прогон идёт минуты.

**Итог 6 октября 2026.** Первый прогон — 70,9 % за 9,5 мин: 564 выживших, 167 непокрытых. `stryker_survivors.cs` получил сводку по файлам (`-- --by-file`) и отбор по файлу. Разобраны обработчики сохранения, защита входа, места, даты и форма операции. Ошибок в коде нет, непроверенного поведения — девять мест, на каждое тест:
- правка операции проходит межтабличные правила — снятый вызов проверки при правке не ловил ни один тест;
- переименование счёта, группы и подкатегории в занятое имя отвергается — проверялось только заведение;
- подкатегория правится на месте: имя в другом регистре и значок;
- правка счёта меняет тип и ставит «скрытый»;
- форма открывает записанную операцию с категорией, местом и заметкой, перевод между валютами — с суммой зачисления; расход, переделанный в перевод, теряет категорию и место;
- новое место из формы операции оповещает справочник мест, знакомое — нет;
- справочник мест: порядок по частоте на трёх местах (на двух перевёрнутое сравнение давало тот же порядок), подпись — по самой частой подкатегории;
- защита входа: пауза после перезагрузки идёт дальше, а не стоит; потерянный след снимает и заслонку, не только защиту;
- шапка дня в ленте пишет год только у чужого года.

Точечные прогоны: обработчики сохранения — 97,2 %. Каждый новый тест убил своего мутанта. Повторный полный прогон — 74,8 % за 9 мин: 420 выживших, 166 непокрытых. Часть роста дали исключённые настройки EF и `TimeZoneCities`, их ложные выжившие больше не считаются. Оценка снята до ревью: оно убрало из пропускаемых методов шаблон `*Log*` — тот задевал не журналирование (его в `src` нет), а включение журнала базы `EnableWriteAheadLogAsync`. Следующий прогон посчитает и его мутантов.

Не добиваются — мутация не меняет поведения или тестом её не подстроить:
- проверки `null` в проекциях EF — запрос даёт тот же `NULL`;
- ослабленное условие дат в итогах дня счёта (`||` вместо `&&`) — читается больше дней, а сверяются только дни страницы;
- `Open()` перед резервным копированием SQLite — копирование открывает базу само;
- удаление журнала рядом с базой при откате — в тестах его к этому моменту нет: последнее штатно закрытое соединение сливает журнал в базу и удаляет его. После сбоя на устройстве журнал может остаться, поэтому удаление нужно; тестом этот случай не подстроить;
- `^=` вместо `|=` у флага изменений.

Остальное — ветки моделей представления: подписи, уведомления о свойствах, видимость клавиатуры. Их смотрят по сводке, когда правят экран.

## 4. Повторяемые сценарии на эмуляторе

- [x] Помощник `tools/ui.cs` читает цепочку команд из файла.
- [x] Пять–семь сценариев: счёт, операция, правка, удаление, нарушенное правило, отчёт, ПИН-код. Каждый заканчивается проверкой журнала падений — падение молчит.
- [x] Прогон на чистом эмуляторе отладочной сборкой и релизным APK перед тегом: отсечение кода ломает отражение только в релизе. Сначала проверить, хватает ли на чистом эмуляторе места под релизную установку.
- [x] Порядок прогона — в навык `emulator`.

**Итог 6 октября 2026.** Помощник получил три вещи:
- `script <файл>` — строка сценария идёт отдельной цепочкой со своим номером, сбой называет файл и строку;
- `nocrash` — проверку журнала, которая обрывает цепочку;
- сравнение подписей без разницы между обычным и неразрывным пробелом. Заодно `wait` по подписи, которая на экране дважды, больше не падает с «неоднозначно».

Сценарии `tools/scenarios/01…07`: первый счёт, расход, правка из ленты, три уровня отчёта, удаление, занятое имя счёта, ПИН-код с неверным и верным кодом. С чистой установки вся цепочка зелёная на отладочной сборке (5 мин сценариев и минута развёртывания) и на релизном APK. Релизный APK для эмулятора — `-r android-x64`: публикация идёт минуту. Места на чистом AVD — 3 ГБ, запас снижать не нужно. Ревью добавило `nocrash` перед холодным стартом в сценарии ПИН-кода (`start` чистит журнал, и падение при задании кода пропало бы) и номер строки к ошибке разбора сценария (незакрытая кавычка).
