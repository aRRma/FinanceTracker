# Разбор · 6 октября 2026

Что есть сейчас, что и чем ловить, что из этого вышло в план. План — [PLAN.md](PLAN.md), статус — [README.md](README.md).

## Что решили не делать

| Что | Почему |
|---|---|
| Сбор действий пользователя (Firebase Analytics, Amplitude) | отвечает на вопрос, что делают тысячи пользователей; пользователь один — его проще спросить. Отправляет данные о финансовом поведении в чужое облако. App Center закрыт в 2025 году |
| Облачные сервисы сбоев (Sentry, Crashlytics) | хорошие инструменты, у Sentry есть пакет для MAUI и нативные падения, но им нужна сеть, а отчёт уходит третьей стороне. Вернуться вместе с обменом: отчёты пойдут на свой сервер |
| Аудит изменений данных | появится сам вместе с обменом: журнал изменений для синхронизации и есть аудит. Поля (`updated_at_utc`, мягкое удаление) уже в схеме |
| Постоянный замер скорости | задержек на глаз нет; разовый замер профилировщиком полезнее постоянного сбора |

## Что есть сейчас

| Где | Что со сбоем | Что теряется |
|---|---|---|
| `Guarded.Run`, `Guarded.Execute`, `Navigator.Go` | сообщение пользователю, `Android.Util.Log.Error` с тегом `Finance` | на телефоне журнал Android не прочитать, система затирает его за минуты |
| `ScreenViewModel.OnChanged` → `ReloadFailed` | отдаёт сбой странице, та — в `Guarded` | то же |
| `DatabaseBootstrapper` | заворачивает в `DatabaseMigrationException` с понятным текстом | исходная ошибка — только вложенным исключением, в журнал Android её пишет `Guarded` |
| `DevicePinStore.ReadAsync` | `Log.Warn`, след ПИН-кода снимается | то же |
| `DataPage`, `ExportPage`, `RecoveryHandler`, `TimeZonePage` | ожидаемые ошибки, показываются текстом | это не сбои, отчёт не нужен |
| Сбой вне обработчиков: таймер, поток, фоновая задача | **ничего не подключено** — нет ни `AppDomain.UnhandledException`, ни `AndroidEnvironment.UnhandledExceptionRaiser` | процесс закрывается молча |
| Нативное падение, исключение внутри Java, зависание | **ничего** | всё |

`MauiProgram` подключает только `builder.Logging.AddDebug()` — в релизе он ничего не пишет. В манифесте
нет разрешения на сеть и выключено сохранение данных системой Android (`allowBackup="false"`) — отчёты в файле приложения
никуда сами не уедут.

## 1. Отчёты в файле

**Источники записи:**
- `Guarded` и `ReloadFailed` — уже собирают все сбои обработчиков и перечитывания; достаточно дописать запись в файл.
- `AndroidEnvironment.UnhandledExceptionRaiser` — главный путь для MAUI на Android: исключение .NET, уходящее в Java.
- `AppDomain.CurrentDomain.UnhandledException` — исключения в потоках.
- `TaskScheduler.UnobservedTaskException` — забытые задачи; процесс не роняет, пишется как предупреждение.
- Свой `Java.Lang.Thread.DefaultUncaughtExceptionHandler` — исключение внутри Java: пишет стек (в плане — без сообщений)
  и передаёт прежнему обработчику, чтобы система закрыла процесс как обычно.
- Подключение — как можно раньше, в `MainApplication`: сбой в `MauiProgram.CreateMauiApp` иначе не попадёт.

**Не пишется:** `DomainException` — это нарушенное правило, а не сбой, и в его тексте бывают имена.
`DatabaseMigrationException` пишется вместе с вложенным исключением — именно оно и нужно.

**Отчёт о сбое:** время в UTC (в плане — у `TimeProvider`: отчёты создаются раньше контейнера с `IClock`), вид (пойманный, необработанный .NET, Java, предупреждение,
прошлое завершение), версия и сборка приложения, версия Android, модель, `exception.ToString()`
с вложенными, след действий (пункт 3). В релизе с полным AOT имена методов в стеке есть, номеров строк нет — для поиска причины хватает.

**Хранение:** текстовый файл в `FileSystem.AppDataDirectory`, отдельно от базы; текущий до 256 КБ и один
предыдущий. Трассы зависаний и нативных падений целиком не хранятся: из них в отчёт идёт только стек (пункт 2).

**Текст исключения — не всегда.** `FormatException` несёт введённую строку, `ArgumentOutOfRangeException` — значение
аргумента, так что текст пишется только у типов из белого списка; у остальных — тип и стек.

**Отступления от правил проекта, обосновать комментарием:**
- запись при падении синхронная: процесс умирает, асинхронная не успеет;
- обработчик падения не бросает ничего: свой сбой глушит, иначе потерялся бы исходный. Фильтр у `catch` всё равно нужен (`when (error is not OperationCanceledException)` или перечень) — голый `catch (Exception)` запрещён.

## 2. Причины прошлых завершений

`ActivityManager.GetHistoricalProcessExitReasons(null, 0, 0)` при старте — с Android 11, у нас минимум Android 16.

| Причина | Что даёт | Польза |
|---|---|---|
| `REASON_CRASH_NATIVE` | с API 31 — `getTraceInputStream`: трасса нативного падения в **protobuf** (схема `tombstone.proto`) — сигнал, сообщение, потоки, стек с именами функций системных библиотек | падение в `libhwui` видно до функции |
| `REASON_ANR` | текстовый дамп потоков | на чём встал поток интерфейса |
| `REASON_CRASH` | только `getDescription` — формат не гарантирован | полный стек уже записали обработчики пункта 1 |
| `REASON_LOW_MEMORY`, `REASON_FREEZER`, `REASON_SIGNALED`, `REASON_OTHER` | одна строка | объясняет «открыл, а форма пустая»: процесс убит в фоне |
| `REASON_EXIT_SELF` с кодом не 0 | пустое описание | сбой .NET вне главного потока (поток, таймер) — проверено на эмуляторе |
| `REASON_EXIT_SELF` с кодом 0, `REASON_USER_REQUESTED`, `REASON_USER_STOPPED`, `REASON_PACKAGE_UPDATED`, `REASON_PACKAGE_STATE_CHANGE` | — | обычные завершения, отчёта не дают. `EXIT_SELF` с кодом 0 — перезапуск после восстановления (`AppRestart` выходит `Exit(0)`) |

**Подробности:**
- обработанные записи помнятся меткой времени последней в `Preferences`, иначе каждая давала бы отчёт на каждом запуске;
- **`setProcessStateSummary(byte[])`** — до 128 байт, которые приложение кладёт заранее и получает назад
  в записи о завершении (`getProcessStateSummary`). Туда — текущий экран и последнее действие: даже о нативном
  падении, когда .NET уже мёртв, известно, где оно случилось. Предел в документации не назван; на эмуляторе — 128 байт,
  на 129 вызов бросает `IllegalArgumentException` «Data size is too large», так что обрезка обязательна;
- система держит последние 16 записей на пакет (проверено): если после падения долго не открывать
  приложение, а оно перезапускается, причину можно не застать;
- **приватность трассы нативного падения:** в ней бывают куски памяти вокруг регистров, а в памяти — строки из базы.
  Поэтому на телефоне из неё вынимаются только сигнал и стек упавшего потока; остальное, включая сообщение
  о прерывании, не хранится — в нём бывает текст исключения .NET.
  Разбор — свой небольшой читатель формата protobuf (около сотни строк) по полям `tombstone.proto`, без новой библиотеки.

## 3. След действий

Кольцо из 30 последних событий в памяти; выписывается в отчёт о сбое. На диск постоянно не пишется:
каждый переход — лишняя запись во флеш, а при падении след и так уходит в файл.

| Источник | Как | Что пишется |
|---|---|---|
| Переходы | `Shell.Navigated` в `AppShell` — одно место на все переходы, включая «назад» | маршрут **без параметров** (`?id=…`, `?kind=…` отрезаются) |
| Действия | `[CallerMemberName]` и `[CallerFilePath]` у `Guarded.Run` и `Guarded.Execute` | «TransactionPage.OnSaveClicked» — без разметки каждой кнопки |
| Жизненный цикл | `MainActivity`: `OnStop`, `OnRestart`, смена темы, `OnTrimMemory` | событие; смена темы — прямо про разовое падение |
| Нарушенное правило | `Guarded` (из `FormViewModel` — нет, причина в плане) | только имя члена `Invariant` |

Кольцо принимает только имена из кода (маршрут, файл и метод, член перечисления), а не произвольный текст —
положить туда сумму или имя случайно нельзя. При каждом переходе обновляется и `setProcessStateSummary`.

## Чего это не даст

- процесс убит раньше, чем обработчик записал, — запись придёт только из пункта 2 при следующем запуске и только если её не вытеснили;
- зависание, после которого приложение ожило само, не оставляет записи — система пишет его только в свой журнал;
- номеров строк в стеке релизной сборки нет;
- отчёт сам не приходит и приложение о нём не напоминает: его присылают руками через «Поделиться».

## Как проверять на эмуляторе

| Сбой | Как вызвать | Ожидание |
|---|---|---|
| .NET в обработчике | скрытое действие только в отладочной сборке (`#if DEBUG`, `using` — тоже под ним) | отчёт с видом «пойманный» и следом |
| .NET вне обработчика | то же, бросок из таймера или потока | отчёт «необработанный .NET»; при следующем запуске — `EXIT_SELF` с кодом 1, повтора нет |
| Java | `adb shell am crash ru.finance.tracker` | отчёт от своего Java-обработчика; при следующем запуске — `REASON_CRASH`, повтора нет |
| Нативное | `kill -SEGV` процессу через `run-as` | при следующем запуске — `REASON_CRASH_NATIVE` со стеком и экраном из summary |
| Зависание | главный поток занят дольше 5 с, касания по окну, в окне «не отвечает» — «Закрыть приложение» (`aerr_close`) | при следующем запуске — `REASON_ANR` с трассой |

Убийство в фоне на эмуляторе не воспроизводится: `am kill` записывается как `USER_REQUESTED`, то есть обычное завершение.

## Проверено на эмуляторе · 6 октября 2026

Отладочная сборка на чистом AVD (Android 16), разовая вставка в `MainApplication.OnCreate`, в репозиторий не вошла.
Образцы трасс и журнал проверки — в папке `artifacts` задачи (в git не попадает); данных пользователя в образцах нет, база тестовая.

| Сбой | Сработали обработчики, по порядку | Запись системы при следующем запуске |
|---|---|---|
| .NET на главном потоке | `UnhandledExceptionRaiser` → Java-обработчик (`JavaProxyThrowable`) → `AppDomain.UnhandledException` | `REASON_CRASH`, описание «crash», трассы нет |
| Исключение Java, брошенное из .NET на главном потоке | те же три | `REASON_CRASH` |
| `am crash` (исключение внутри Java) | Java-обработчик → `AppDomain.UnhandledException`; `UnhandledExceptionRaiser` — нет | `REASON_CRASH` |
| .NET в потоке, в таймере | только `AppDomain.UnhandledException` (`IsTerminating`) | `REASON_EXIT_SELF`, код 1, описание пустое |
| Забытая задача | `UnobservedTaskException` после сборки мусора; процесс живёт | — |
| `kill -SEGV` | ни один | `REASON_CRASH_NATIVE`, код 11, трасса protobuf 280 КБ |
| Зависание, пользователь закрыл | — | `REASON_ANR`, описание «user request after error: Input dispatching timed out…», текстовая трасса 56 КБ |
| Зависание, поток ожил сам | — | **ничего**: система пишет ANR только в свой журнал |
| `am kill` в фоне, `am force-stop` | — | `REASON_USER_REQUESTED`, описание «[KILL BACKGROUND]» или «[FORCE STOP]» |

Что из этого следует:
- **один сбой — до трёх вызовов обработчиков:** отчёт пишет первый, остальные видят признак «уже записано» и молчат;
- прежний Java-обработчик — `mono.android.XamarinUncaughtExceptionHandler`; свой встаёт перед ним и отдаёт ему исключение дальше;
- синхронная запись в файл из каждого обработчика успевала до смерти процесса — во всех прогонах;
- summary приходит в каждой записи о завершении, включая нативное падение и force-stop;
- после обновления пакета в истории была одна запись — о самом обновлении: похоже, установка поверх сбрасывает историю. Сбой перед обновлением теряется — с этим можно жить;
- force-stop процесса с неразрешённым зависанием приносит трассу зависания в записи `USER_REQUESTED`;
- в нативной трассе есть список открытых файлов — путь к базе там виден, — карты памяти и её куски: решение хранить только сигнал, сообщение и стек упавшего потока подтверждается.
