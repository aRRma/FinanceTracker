# План: отчёты о сбоях

Основание — [SUMMARY.md](SUMMARY.md). Отметки о готовности ставятся только здесь, в [README.md](README.md) — этап целиком.

Общее для всех этапов: новая проверка ломается нарочно в момент написания и падает с внятным сообщением;
в конце этапа — полный `dotnet test` со сверкой числа тестов, `dotnet build Finance.slnx`; правка, видная
в интерфейсе, — проверка в эмуляторе (чистый `pixel_7_clean`).

Спрашивать по одному, когда до них дойдёт этап.

- [x] **Сообщение после падения:** не показывать — отчёты тихо ждут в «О программе». Решено пользователем 6 октября 2026.
- [x] Трасса нативного падения разбирается на телефоне, хранится только стек — рекомендовано в разборе, принято вместе с планом 6 октября 2026.

## 1. Отчёты о сбоях в прикладном слое

`Finance.Application/Infrastructure/Diagnostics`.

- [x] Отчёт о сбое (`CrashReports`, `CrashReport`, `CrashKind`, `DeviceInfo`): вид, время UTC, версия приложения и сборки, Android, модель, тип исключения и стек с вложенными. Сведения об устройстве — параметром из `Finance.App`, не через MAUI. Время — у `TimeProvider`, а не у `IClock`: отчёты создаются раньше контейнера служб, где живут часы; источник у них один. След добавляется на этапе 3.
- [x] **Текст исключения — только у типов из короткого белого списка** (`CrashDescription`: сорванная миграция, `SqliteException`, три типа с текстом без значений); у остальных — тип и стек. `InvalidOperationException` в список не входит: сообщения о пропавшей записи называют группу по имени. Вложенные — по тому же правилу, до восьми уровней.
- [x] Файл: синхронная запись с дозаписью, текущий до 256 КБ и один предыдущий; чтение от новых к старым; очистка. Запись и смена файла — под одной блокировкой.
- [x] Сбой самой записи не бросается наружу (фильтр у `catch`); почему синхронно — комментарий.
- [x] `DomainException` и отмена не пишутся; `DatabaseMigrationException` — с вложенным.
- [x] Регистрация в `AddFinance`: готовый объект от платформы или, если его нет, отчёты рядом с базой.
- [x] Тесты `CrashReportsTests`: формат, белый список, вложенные и составные, смена файла, порядок, одновременная запись, оборванная запись в конце и в середине, строка, похожая на служебную, очистка, сбой записи. Нарочной поломкой проверены белый список, отсев правил, блокировка, предел глубины и регистрация. Тест оборванной записи нашёл ошибку: следующий отчёт склеивался с оборванной строкой — запись теперь начинает с перевода строки.

## 2. Перехват сбоев в приложении

- [x] `CrashCatcher` в `MainApplication.OnCreate`: `AndroidEnvironment.UnhandledExceptionRaiser`, `AppDomain.CurrentDomain.UnhandledException`, `TaskScheduler.UnobservedTaskException` (предупреждение) — до `CreateMauiApp`; отчёты создаются там же и уходят в `AddFinance` готовыми.
- [x] Свой `JavaCrashHandler`: пишет и отдаёт прежнему обработчику. Обёртка .NET над исключением Java знает только управляемую часть стека — у падения внутри Java она пуста, — поэтому стек берётся у Java (`Log.GetStackTraceString`) и пишется `WriteFatalJava` без сообщений: в сообщении обёртки над исключением .NET лежит его текст.
- [x] Один сбой — один отчёт (`WriteFatal`): пишет первый обработчик, остальные молчат. Тест, в том числе с одновременными вызовами.
- [x] `Guarded.ReportAsync` (через него идёт и сбой перечитывания экрана) и сорванная миграция в `DataPage` пишут отчёт; журнал Android под тегом `Finance` остаётся — его читает `tools/ui.cs -- crash`.
- [x] `DevicePinStore.ReadAsync` — отчёт-предупреждение.
- [x] Отладочный вызов сбоя `DebugCrash` (только Debug): `am start -n ru.finance.tracker/ru.finance.tracker.MainActivity --es debug_crash вид --es debug_crash_id номер`, виды `caught`, `ui`, `thread`, `timer`, `task`, `java` и с этапа 4 `anr`. Номер у каждого вызова свой: упавшее приложение система поднимает с тем же намерением, и без номера сбой повторялся на каждом перезапуске — так и было при первой проверке.
- [x] Проверка в эмуляторе: шесть видов `DebugCrash` и `am crash` — семь отчётов, по одному на сбой, вид — от первого обработчика. Релизная сборка решения — без ошибок и предупреждений.
- [x] Ревью этапов 1–2 (6 октября 2026), исправлено с тестами и нарочной поломкой: признак «падение записано» снимается, если запись не удалась; описание сбоя — под той же защитой, что запись (текст и стек исключения моста Java бросают в развалившейся среде); оба файла читаются под блокировкой записи — смена файла между чтениями теряла отчёты; подключение перехвата не роняет запуск, если сведения об устройстве не прочитались; пустой стек Java (так Android отдаёт цепочку с `UnknownHostException`) заменяется классом; отладочный сбой с неизвестным видом не тратит номер. Не принято: обёрнутые в составное исключение нарушенное правило и отмена из забытой задачи пишутся — пользователь их не видел, а текст правила в отчёт не попадает.
- [ ] Отчёты на релизном APK: без экрана их не прочитать (`run-as` у релиза закрыт) — проверяется на этапе 6, когда экран готов.

## 3. След действий

- [x] `ActionTrail`: кольцо на 30 событий; принимает только маршрут, файл и метод, член `Invariant`, `LifecycleEvent` — без свободной строки. Создаётся вместе с `CrashReports` (раньше контейнера), выписывается в каждый отчёт после строки `--- trail`.
- [x] Маршрут без параметров; от пути файла — только имя.
- [x] Переходы — `AppShell.OnNavigated`; обработчики — `[CallerFilePath]` и `[CallerMemberName]` у `Guarded.Run` и `Guarded.Execute` (вид `run`: это не только нажатия, но и появление экрана, прокрутка); запуск, уход в фон, возврат, смена темы, `OnTrimMemory`; нарушенное правило — именем, из `Guarded`. Из `FormViewModel` — нет: правило формы показано у поля и сбоем не кончается, а след пришлось бы протаскивать через конструкторы пяти моделей; само нажатие «Сохранить» в след попадает.
- [x] `setProcessStateSummary` при каждом переходе и обработчике: экран и последнее действие, до 128 байт с обрезкой по символам. На эмуляторе система держит её в записи о завершении (`state=33 bytes` у падения после «Балансов»).
- [x] Тесты `ActionTrailTests`: порядок, вытеснение, параметры маршрута, имя файла с разделителями Windows и Linux, сводка, обрезка по байтам UTF-8 без разрыва символа, след в отчёте. Нарочной поломкой проверены отрезание параметров и обрезка по байтам.
- [x] Проверка в эмуляторе: вкладки, уход в фон и возврат, затем сбой — в отчёте запуск, все переходы, обработчики появления экранов, `Stopped`, `TrimMemory`, `Restarted`.

## 4. Причины прошлых завершений

- [x] `IExitHistory` в прикладном слое, `DeviceExitHistory` на `ActivityManager` в `Platforms/Android`; трасса читается только у нативного падения и зависания.
- [x] `PastExits` при старте, в фоне, после сборки служб: записи новее метки из настроек устройства (`IDevicePreferences`); метка — момент последней записи, в том числе пропущенной. Обычные завершения (`EXIT_SELF` с кодом 0, `USER_REQUESTED`, `USER_STOPPED`, `PACKAGE_UPDATED`, `PACKAGE_STATE_CHANGE`) пропускаются; `EXCESSIVE_RESOURCE_USAGE` — не обычное: на эмуляторе система убила им процесс в фоне за «excessive binder traffic during cached».
- [x] `REASON_CRASH` и `EXIT_SELF` с кодом не 0, о которых уже есть отчёт обработчика, второй раз не пишутся — сверка по времени (окно 10 с до записи системы). Pid в отчёте не хранится, хватило времени. Описание от системы у `REASON_CRASH` не пишется: в нём может оказаться текст исключения.
- [x] Зависание (`AnrTrace`): тема и стек главного потока — и Java-стек `"main"`, и нативный, с `sysTid` = pid: на эмуляторе пришёл только нативный. До 16 КБ, внутри отчёта. Зависание, после которого поток ожил, система не записывает.
- [x] Нативное падение (`NativeTrace`, свой `ProtoReader`): сигнал и стек упавшего потока. **Сообщение о прерывании не пишется** — по решению пользователя хранится только стек, а в сообщении бывает текст исключения .NET. В коде — «нативная трасса», не `Tombstone`.
- [x] Тесты `PastExitsTests`: обычные завершения, метка, сверка с отчётом обработчика, сводка, нативная трасса на образце, собранном тестовым `Proto` (с регистрами, памятью, открытыми файлами, сообщением о прерывании и вторым потоком — в отчёт не попадает ничего из этого), испорченная трасса, трасса зависания и её предел. Нарочной поломкой проверены стек только упавшего потока, `EXIT_SELF` с кодом, сверка с обработчиком, предел трассы зависания.
- [x] Ревью этапов 3–4 (6 октября 2026), исправлено с тестами и нарочной поломкой: метка не уходит за запись, которую не удалось записать, — иначе система её больше не отдаст; нативное падение сразу за отчётом обработчика — та же смерть (среда .NET закрывает процесс прерыванием), второго отчёта нет; отчёты читаются по моменту сбоя, а не по порядку записи — отчёт о прошлом завершении пишется при следующем запуске; порча посреди нативной трассы не стирает уже прочитанный сигнал и кадры; из трассы зависания — только секция своего процесса; `OnTrimMemory` уровня `UiHidden` (приходит при каждом уходе в фон) в след не пишется; сводка для системы отправляется из пула потоков, частые события сливаются в одну отправку, а сбой отправки глушится.
- [x] Проверка в эмуляторе: `kill -SEGV` на вкладке «Отчёт» — отчёт с экраном `//report`, сигналом и стеком; зависание (`DebugCrash` вида `anr`, закрытие в окне «не отвечает») — тема, экран, стек главного потока; `am crash` — один отчёт обработчика, без второго от системы. Убийство в фоне эмулятор не воспроизводит: `am kill` записывается как `USER_REQUESTED`.

## Отложено и отклонено

- **Облачный сервис сбоев (Sentry) — отложен** до обмена с сервером: нужна сеть, отчёт уходит третьей стороне.
- **Аудит изменений данных — отложен:** появится с журналом изменений обмена.
- ~~Сообщение «приложение закрылось с ошибкой» при следующем запуске~~ — пользователь выбрал тихий вариант: отчёты ждут в «О программе».
- ~~Имя со словом «журнал»~~ — словарь уже запрещает «журнал» как другое имя ленты счёта, а «журналом изменений» назван обмен.
- ~~Текст любого исключения в отчёте~~ — в текстах бывают введённые значения; пишется только у белого списка типов.
- ~~Сбор действий пользователя в облако~~ — пользователь один, данные о финансовом поведении в чужое облако не уходят.
- ~~Постоянный замер скорости~~ — задержек нет; при появлении — разовый замер профилировщиком.
- ~~След действий на диске на каждое событие~~ — лишняя запись во флеш; след уходит в файл при сбое, экран — в summary.
- ~~Трасса нативного падения целиком~~ — в ней бывают куски памяти с данными пользователя.
- ~~Чтение журнала Android (`logcat`) самим приложением~~ — приложение перехватывает свои сбои само, чужие строки не нужны.
